# LAN Cowork のネットワーク挙動（何が LAN 上で起きるか）

> 対象: v4.538.0 以降の Rust standalone（`yu-server`）。Python バックエンド併用（hybrid）構成については
> 末尾の「Python 版との違い」を参照してください。

このページは **「LAN Cowork を有効にすると、あなたのマシンがネットワーク上で何を始めるのか」** を
一枚にまとめたものです。設定を変える前に目を通してください。

---

## 要点

- **既定では何もしません。** Rust standalone は、後述の設定で明示的に有効化しない限り、
  LAN 上で待受けも告知も行いません。
- 有効にすると、**同一 LAN 上の他ノードから発見される状態**になります。これは設計どおりの動作です。
- **PIN の有無は discovery の告知を止めません。** 詳しくは「PIN との関係（誤解しやすい点）」を参照。

---

## 有効にすると始まること

| 動作 | 内容 |
|---|---|
| **UDP 待受け** | `0.0.0.0:19850` を bind します（全インタフェース） |
| **定期的な告知** | 10 秒ごとに、署名付きの HELLO を `255.255.255.255:19850` へ broadcast します。内容には自ノードの ID・公開鍵・API ポート・ホスト名などが含まれます |
| **他ノードの登録** | 受信した HELLO の署名を検証し、相手ノードを自分のピア一覧へ記録します（TOFU） |
| **inbound HTTP の受付** | 下表の peer 用エンドポイントが応答を返し始めます |
| **ローカル配信** | 受理したピアイベントを、ログイン済みの画面が購読する SSE（`/api/events/stream`）へ流します |
| **期限切れ掃除** | 60 秒ごとに、期限切れのペアリング要求と平文 PIN をメモリから掃除します |

### inbound で受け付けるエンドポイント

| エンドポイント | 認証 |
|---|---|
| `GET /ext/lan_cowork/api/peer/discover` | **セッション不要**（ピア一覧の照会） |
| `GET /ext/lan_cowork/api/peer/status` | **セッション不要**（自ノードの記述子） |
| `POST /ext/lan_cowork/api/peer/register` | **セッション不要**（ピアの自己登録。登録先はサーバ側で検証） |
| `POST /ext/lan_cowork/api/peer/pair/request` / `pair/verify` | **セッション不要**（ペアリング開始。未ペアの相手はセッションを持ち得ないため） |
| `POST /ext/lan_cowork/api/peer/token/renew` | 署名 + nonce（Bearer 不要） |
| `POST /ext/lan_cowork/api/peer/event` / `heartbeat` | 署名 + Bearer トークン |

「セッション不要」は**認証が無い**という意味ではなく、**ログインセッションを要求しない**という意味です。
ペアリング済みでない相手はセッションを持てないため、この 5 経路だけが例外として開いています。
それ以外の経路は従来どおりログインが必要です。

## 有効化・無効化のしかた

`config.json` の **`extensions` セクション**で切り替えます。

```json
{
  "extensions": {
    "builtin-lan-cowork": {
      "enabled": true
    }
  }
}
```

- **キーが無い場合は「無効」** です（Rust standalone）。
- 反映には**再起動**が必要です。
- 一時的に切り替えたい場合は起動オプションでも指定できます。優先順位は
  **コマンドライン > `config.json` > 環境変数 > 既定** です。

| 方法 | 有効化 | 無効化 |
|---|---|---|
| コマンドライン | `--native-daemon` | `--no-native-daemon` |
| 環境変数 | `YU_LAN_COWORK_NATIVE_DAEMON=1` | 同 `=0` |

> 環境変数は `1` / `true` / `yes` のみを「有効」と解釈します。`on` や `Y` は**無効**として扱われます。

### 有効になっているかの確認

```bash
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5000/ext/lan_cowork/api/peer/status
```

| 応答 | 意味 |
|---|---|
| `200` | 有効。ピア機能が動作しています |
| `405` | **無効**（機能自体が組み込まれていない状態） |
| `503` | 有効だが準備できていない（ノード固有の鍵が未生成、または内部の初期化に失敗） |

> **画面の拡張機能一覧の表示は当てになりません。** 拡張機能の一覧では LAN Cowork が「有効」と
> 表示されることがありますが、これは同梱情報に基づく表示で、**上記の daemon が実際に動いているか
> どうかとは別**です。判断は上のエンドポイントの応答か、起動ログの
> `native_daemon=...` の行で行ってください。

## PIN との関係（誤解しやすい点）

**PIN を設定していなければ LAN からは何も触れない、と考えるのは正確ではありません。**

- **正しい**: `--lan`（全インタフェースで待受け）を使うには PIN が必須で、無ければ起動が中止されます。
  既定の待受けは `127.0.0.1` なので、**通常起動では HTTP 面は LAN から到達できません**。
- **注意 1**: `--host` に LAN の IP を直接指定した場合、この PIN の必須チェックは通りません。
  さらに PIN 未設定時はログインゲート自体が開くため、**PIN 無しで LAN に晒すことは避けてください**。
- **注意 2**: **UDP の告知は PIN の有無とは無関係です。** 有効化されていれば、PIN 未設定でも
  10 秒ごとに LAN へ自分の存在を broadcast します。PIN が抑えるのは HTTP 面の露出だけです。

つまり **PIN は HTTP 面の露出を抑えますが、discovery の告知は止めません。**

### loopback だけで待ち受けている場合（v4.539.0 以降）

待受けアドレスが loopback のみ（既定の `127.0.0.1`、デスクトップ版もこれに当たります）の場合、
**このノードは LAN へ告知しません**。告知しても他ノードから接続できないためです。
起動後に一度だけ次の警告がログに出ます（INFO ではなく WARN なので既定でも見えます）。

```
LAN Cowork discovery inactive: server listens on loopback only; bind a LAN address or use --lan
```

LAN で使いたい場合は、待受けアドレスを LAN のものにするか `--lan` を使ってください
（`--lan` は PIN 必須です）。

> v4.539.0 より前は、loopback 待受けのままでも LAN IP を告知していました。相手からは発見できても
> 接続できない状態になるため、告知しない挙動へ改めています。

## 有効化する前に知っておくこと

- **無効化しても、有効だった間に記録されたピア情報は自動では戻りません。** 加えて、
  **有効化して最初に起動した時点で**、古いピア記録の掃除が走ります
  （最後に到達できてから 7 日以上経過した記録、および未ペアのまま 1 時間経過した記録が削除されます）。
  切り替えの前に `tags.db` のバックアップを取ることを勧めます。
- 受け取ったピアイベントは、ログイン済みの画面が購読する SSE へ流れます。**内容は相手ノード由来の入力**です
  （送信元の ID はサーバ側で認証済みの値に置き換えられます）。
- ログに残るのは**件数と種別と送信元 ID のみ**で、イベントの中身は記録されません。
- 動作状況を確認したい場合は、ログレベルで INFO を有効にしてください
  （例: `RUST_LOG=yu_server=info`）。既定のままでは、ピアイベントの受信を示す行は出力されません。

## Python 版との違い

| | Python バックエンド併用（hybrid） | Rust standalone |
|---|---|---|
| 既定 | **有効**（`config.json` に項目が無ければ有効） | **無効**（明示的に有効化が必要） |
| 実装 | Python 拡張が担当 | `yu-server` が担当 |

**Rust standalone は意図的に「既定で無効」にしています。** 更新しただけでネットワーク上の挙動が
変わることを避けるためです。hybrid 構成の挙動は従来から変わりません。

> 過去のドキュメントでは有効化の設定を `{"lan_cowork": {"enabled": true}}`（最上位）と案内していましたが、
> **この位置のキーはどの実装からも読まれません。** 上記の `extensions` セクションが正しい位置です。
