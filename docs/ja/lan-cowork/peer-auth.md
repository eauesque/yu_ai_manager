# ピア間 PIN 認証・トークンペアリング

**実装バージョン**: 4.92.0
**関連ファイル**: `extensions/builtin_lan_cowork/`, `core/lan_cowork_core/`

---

## 概要

v4.92 以前は、LAN 上のピア間通信において `X-Peer-Id` ヘッダのみで相手を識別していました。
このヘッダは LAN 内の誰でも偽造できるため、セキュリティが不十分でした。

v4.92 から、**PIN 承認ベースのトークンペアリング**方式へ移行しました。

- 初回接続時に「ペアリングリクエスト」を送信
- 相手管理者が管理画面で承認し、6桁 PIN を発行
- PIN を入力すると Bearer トークン（30 日有効）が発行される
- 以降の通信は `Authorization: Bearer <token>` で認証

旧 `X-Peer-Id` ヘッダ方式は設定で互換性を保持できますが、DELETE 系操作は常に新認証が必要です。

---

## ペアリングフロー

```
[接続元ピア A]                        [接続先ピア B]
       |                                      |
       |--- POST /api/lan/pair/request ------->|
       |    (peer_id, display_name, public_key)|
       |                                      |
       |                              管理者が /lan-cowork/peers で確認・承認
       |                                      |
       |<--- SSE: peer_pairing.pin_ready ------|
       |    (6桁 PIN, 有効期限 5 分)           |
       |                                      |
       |--- POST /api/lan/pair/verify -------->|
       |    (peer_id, pin)                     |
       |                                      |
       |<--- 200 OK: { token, expires_at } ----|
       |    (Bearer トークン, 30 日有効)        |
       |                                      |
       |--- 以降 Authorization: Bearer <token> |
```

### 各ステップの詳細

| ステップ | エンドポイント | 説明 |
|----------|---------------|------|
| 1. リクエスト送信 | `POST /api/lan/pair/request` | ピア ID・表示名・公開鍵を送信 |
| 2. 承認待ち | — | 管理者が `/lan-cowork/peers` で確認 |
| 3. PIN 発行 | — | 管理者が承認ボタンを押すと 6桁 PIN を生成（5 分有効） |
| 4. PIN 検証 | `POST /api/lan/pair/verify` | PIN を送信し Bearer トークンを受け取る |
| 5. 認証済み通信 | — | `Authorization: Bearer <token>` ヘッダを付与 |

## 管理画面 (`/lan-cowork/peers`)

### 承認待ちリクエスト

新しいピアからペアリングリクエストが届くと、管理画面の「承認待ち」タブに表示されます。

- **承認**: PIN を生成し、リクエスト元のピアへ SSE で通知します
- **却下**: リクエストを削除します。リクエスト元には 403 が返ります

### 接続ピア一覧

ペアリング済みのピアと、各トークンの有効期限を一覧表示します。

| 列 | 内容 |
|----|------|
| 表示名 | ピアの名前 |
| IP アドレス | 最後に確認された接続元 IP |
| 有効期限 | Bearer トークンの有効期限（30 日） |
| 最終接続 | 最後のハートビート時刻 |
| 操作 | トークン失効ボタン |

### トークンの失効

「失効」ボタンを押すと、対象ピアの Bearer トークンを即座に無効化します。
次回の通信時に 401 が返り、ピアは自動的に再ペアリングを試みます。

## 設定項目

設定は `config.json` の `lan_cowork` セクション、または設定画面の「LAN 共同作業」タブで変更できます。

> **注記**: IP アドレスによる接続チェック（`ip_check_mode`）は Ed25519 署名検証への完全移行により廃止されました。

### `protect_heartbeat`

ハートビートエンドポイントにも Bearer トークン認証を要求するかどうかを指定します。

- `true`: ハートビートにも Bearer トークンが必要（デフォルト）
- `false`: ハートビートは IP + peer_id チェックのみで通過

> **補足**: ペアリング未実施のピアからのハートビートは、`true` でもトークンなしで通過します（`peer_tokens` にエントリがない＝まだペアリングしていない状態と判定し、IP + peer_id チェックのみで受け入れます）。一度ペアリングしてトークンが発行された後にトークンを失った場合は 401 になります。

### `protect_events`

SSE イベントストリーム (`/api/events/`) にも認証を要求するかどうかを指定します。

- `true`: SSE 接続にも Bearer トークンが必要
- `false`: SSE は認証なしで通過（デフォルト: `false`）

## セキュリティノート

### トークンのハッシュ化

発行された Bearer トークンは、データベースに **平文で保存されません**。
scrypt (N=16384, r=8, p=1) でハッシュ化されたうえで保存されます。
DB が流出しても、元のトークンを復元することはできません。

### ログのマスキング

- `Authorization: Bearer <token>` ヘッダはログ出力時に自動的に `Bearer [REDACTED]` に置換されます
- PIN コードもログに残りません

### レート制限

DoS 攻撃やブルートフォースを防ぐため、以下のレート制限が適用されます。

| エンドポイント | 制限 |
|---------------|------|
| `POST /api/lan/pair/request` | 10 件/分/IP |
| `POST /api/lan/pair/verify` | 30 件/分/IP |

PIN は 5 分で自動失効し、1 つのリクエストに対して 1 回しか検証できません。

## トラブルシューティング

### ペアリングリクエストが届かない

- 相手ピアの URL が正しく設定されているか確認してください
- ファイアウォールでポートがブロックされていないか確認してください
- 相手ピアのログで `pair/request` の受信状況を確認してください

### PIN が期限切れになった

PIN の有効期限は 5 分です。期限切れの場合は、管理画面で再度「承認」ボタンを押すと新しい PIN が発行されます。

### トークンが突然使えなくなった

以下の原因が考えられます:

1. 管理者が管理画面でトークンを失効させた
2. 30 日の有効期限が切れた

再ペアリングを実行してください。

### ペアリング済みのはずなのにハートビートが 401 になる

ペアリングは**一方向**です。A が B へペアリングすると「A が B へ認証済みリクエストを送れる」状態になりますが、B が A へ送るリクエストの認証は別途必要です。

例: macOS(A) から Windows(B) へペアリングした場合
- A → B のリクエスト（heartbeat 含む）: 認証済み ✓
- B → A のリクエスト（heartbeat / fleet 再起動 等）: A 側にトークン未発行 → 401 ✗

**対処**: B 側の UI から A へ向けてペアリングリクエストを送り、A 側で承認します（逆方向のペアリング）。

> **fleet 操作（再起動・更新）が目的の場合**: ペアリングとは別に、ターゲットノード側の `allow_remote_update: true` + `allow_update_from` へのチーフ peer_id 追加が必要です。`fleet-admin.md` の「macOS 固有の注意事項」を参照してください。これらは LAN Cowork ページの「Fleet 許可」セクションから GUI で設定できます（`config.json` の手書き不要）。
