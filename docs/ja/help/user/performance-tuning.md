# パフォーマンス調整ガイド

10 万ファイル以上を管理する環境で YU AI Manager を快適に使うためのチューニングガイドです。
デフォルト設定でも多くの最適化が自動で動作しますが、環境に合わせて調整することでさらに改善できます。

---

## 1. 推奨ハードウェア

| 項目 | 最低要件 | 推奨 (10 万ファイル以上) |
|------|---------|------------------------|
| CPU | 2 コア | 4 コア以上 (サムネイル生成が並列化されます) |
| RAM | 4 GB | 8 GB 以上 |
| ストレージ | HDD | **SSD を強く推奨** — データベースの応答速度に直結します |
| ネットワーク | — | LAN 経由で使う場合は 1 Gbps 以上 |

**特に重要**: データベースファイル (`data/tags.db`) は必ず SSD 上に配置してください。
画像ファイル本体は HDD でも問題ありませんが、DB が HDD にあると検索・ブラウジングが著しく遅くなります。

---

## 2. 初回スキャンの最適化

### スキャンルートの分割

大量のファイルを一度にスキャンすると時間がかかります。
Settings > Scan Roots でスキャンルートを複数に分けて登録し、段階的にスキャンすることを推奨します。

- まず最もよく使うフォルダを先にスキャン
- 残りのフォルダはスキャンキューに追加 (自動的に順番に処理されます)
- 同一フォルダを重複登録しても自動で検出・スキップされます

### スキャン中もブラウジング可能

スキャン中でも検索やサムネイル表示は通常通り使えます。
内部的に読み取り専用のデータベース接続を使用しているため、スキャンの書き込み処理がブラウジングをブロックしません。

### スキャン完了後の自動最適化

スキャン完了時にデータベースの統計情報が自動更新 (ANALYZE) されます。
これにより検索クエリの実行計画が最適化され、以降の検索が高速になります。
特別な操作は不要です。

---

## 3. ブラウジング速度の改善

### Service Worker キャッシュ

ブラウザの Service Worker が以下のコンテンツを自動キャッシュします:

| 種類 | キャッシュ上限 | 効果 |
|------|-------------|------|
| サムネイル | 5,000 件 | 2 回目以降のグリッド表示が即座 |
| プレビュー (1200px) | 200 件 | モーダル表示の高速化 |
| 原寸画像 | 50 件 | 最近見た画像の再表示が即座 |

Service Worker はブラウザが自動管理するため、特別な設定は不要です。
キャッシュをクリアしたい場合は、ブラウザの開発者ツール > Application > Storage で操作できます。

### 仮想スクロールの有効化

数千件の検索結果を表示する場合、仮想スクロールを有効にすると描画パフォーマンスが大幅に改善します。

**有効化手順**: Settings > Appearance > 「Virtual Scroll」を ON

仮想スクロールは画面に見えている範囲のカードのみを DOM に描画するため、メモリ使用量と描画負荷が大幅に軽減されます。
数万件規模のライブラリでは有効化を強く推奨します。

### WebP サムネイル

サムネイルは WebP 形式で生成されます (JPEG 比で 30-40% 小さい)。
これにより転送量が削減され、特に LAN 経由のアクセスで効果を発揮します。
設定不要で自動的に適用されます。

## 4. 検索パフォーマンス

### インデックスの効果

データベースには主要な検索パターンに最適化されたインデックスが自動作成されています。
日付順ソート、タグフィルタ、パス検索などが高速に動作します。

**目安**:
- フィルタなし検索: 28 万件規模でも応答 50ms 以内
- タグフィルタ付き検索: 100ms 以内
- パス検索 (FTS5): 50ms 以内

### FTS5 全文検索 vs LIKE 検索

パス検索には FTS5 (Full-Text Search) インデックスが自動的に使われます。
従来の LIKE 検索 (`%keyword%`) と比較して 20-100 倍高速です。

FTS5 が利用できない場合 (古い DB からのアップグレード時など) は自動的に LIKE 検索にフォールバックします。
スキャンを 1 回実行すれば FTS5 インデックスが構築されます。

**日本語検索の注意**: 漢字・ひらがな・カタカナを含む検索は内部的に LIKE フォールバックが使われる場合があります。
これは SQLite の FTS5 トークナイザの制限によるもので、正常な動作です。

## 5. 動画再生の最適化

### Faststart キャッシュ

MP4/MOV ファイルの動画再生を高速化するため、faststart 処理が自動適用されます。
faststart 済みの動画はストリーミング再生が即座に開始されます。

| 項目 | 値 |
|------|-----|
| キャッシュ場所 | `cache/faststart/` |
| 容量上限 | 4 GB (LRU で自動管理) |
| 1 ファイル上限 | 500 MB |
| 対象 | MP4, MOV (WebM は不要のためスキップ) |

**体感改善の目安**:

| ファイルサイズ | faststart なし | faststart あり |
|--------------|---------------|---------------|
| 5-50 MB | 2-10 秒待ち | 約 200ms で再生開始 |
| 50-200 MB | 10-60 秒待ち | 約 500ms で再生開始 |
| 200-500 MB | 数分待ち | 約 1 秒で再生開始 |

### FFmpeg の確認

faststart 処理には FFmpeg が必要です。インストールされていない場合、動画は全ダウンロード後に再生されます。

```bash
ffmpeg -version
```

FFmpeg が PATH に見つからない場合は、[公式サイト](https://ffmpeg.org/download.html) からインストールしてください。

## 6. メモリ使用量の管理

### SQLite mmap

大規模データベース (10 万ファイル以上) では、SQLite の mmap (メモリマップド I/O) が自動的に 1 GB に設定されます。
これにより読み取りクエリが OS のページキャッシュを活用して高速化されます。

**RAM が 4 GB 以下の環境**: mmap がメモリを圧迫する場合があります。
その場合はシステムの空きメモリを監視し、スワップが多発するようであれば他のアプリケーションを閉じてください。

### ブラウザタブの管理

YU AI Manager は SSE (Server-Sent Events) で各タブとリアルタイム通信しています。

- 1 IP あたり最大 10 同時 SSE 接続
- 不要なタブは閉じることで接続リソースが解放されます
- 多数のタブを開くとブラウザのメモリ使用量も増加します

**推奨**: 同時に開くタブは 3-4 個以内に抑えてください。

## 7. トラブルシューティング — 「遅い」と感じたときのチェックリスト

### 基本確認

- [ ] **SSD を使っているか**: `data/tags.db` が HDD 上にある場合、全操作が遅くなります
- [ ] **FFmpeg がインストールされているか**: 動画再生の高速化に必須です
- [ ] **ブラウザのタブ数**: 5 個以上開いていないか確認

### ブラウジングが遅い

- [ ] **仮想スクロールを有効にする**: Settings > Appearance > Virtual Scroll
- [ ] **ブラウザキャッシュをクリアしない**: Service Worker のキャッシュが効いています
- [ ] **スキャン中か確認**: スキャン中は正常に使えますが、初回サムネイル生成に時間がかかります

### 検索が遅い

- [ ] **スキャンを完了させる**: スキャン完了時に ANALYZE が実行され、検索が最適化されます
- [ ] **検索結果が 10 万件超**: 結果を絞り込むフィルタ (タグ、日付、パス等) を追加してください

### 動画再生が遅い

- [ ] **FFmpeg の存在確認**: `ffmpeg -version` で確認
- [ ] **faststart キャッシュ容量**: `cache/faststart/` フォルダが 4 GB を超えていないか (自動管理ですが確認可能)
- [ ] **ファイルサイズ**: 500 MB 超の動画は faststart キャッシュ対象外です。Range 配信で再生されますが初回は若干遅くなります

### サーバー全体が重い

- [ ] **同時アクセス数**: SSE 接続が IP あたり 10 を超えていないか
- [ ] **アップロード中**: 100 MB のアップロード上限に近いファイルを送信中ではないか
- [ ] **Settings > Logs タブ**: サーバーログでエラーや警告を確認

## 8. パフォーマンス指標の目安

正常に最適化された環境での応答時間の目安です。

| 操作 | 28 万ファイル規模 | 10 万ファイル規模 |
|------|-----------------|-----------------|
| グリッド表示 (初回) | 200-500ms | 100-300ms |
| グリッド表示 (キャッシュあり) | 50ms 以下 | 50ms 以下 |
| タグ検索 | 100ms 以下 | 50ms 以下 |
| パス検索 (FTS5) | 50ms 以下 | 30ms 以下 |
| サムネイル (キャッシュヒット) | 5ms 以下 | 5ms 以下 |
| 動画再生開始 (faststart 済み) | 200ms | 200ms |

これらの値を大幅に超える場合は、上記チェックリストを確認してください。

## 高速モード（Rust サーバー）

対応環境では、起動が自動的に Rust 実装のサーバー（`yu-server`）に切り替わります。
設定は要りません。使えないときは静かに Python 版で起動するので、**失敗しても何も壊れません**。

### 一部の機能が使えなくなります

高速モードで起動しているとき、次の 7 経路は **503 を返します**。Python 版でのみ動く機能です。

- Hailo GenAI の LLM 生成・VLM 生成・文脈クリア
- Hailo GenAI のモデル解放
- OpenAI 互換の chat completions・embeddings
- Hailo GenAI チャットの送信

**モデルの状態表示とダウンロードは高速モードでも動きます**（Rust 側に実装があります）。

### これらの機能を使いたいとき

環境変数を付けて起動すれば Python 版になります。

```bash
YU_SKIP_FAST_MODE=1 ./start.sh
```

Windows（PowerShell）:

```powershell
$env:YU_SKIP_FAST_MODE = "1"; .\start.ps1
```

高速モードが有効かどうかは、起動時のログで確認できます。Python 版で起動した場合は
`[fast-mode] Python で起動します: <理由>` が出ます。

### 自分でビルドしたいとき

設定「サーバー」→「高速モード」の**取得方法**で選べます。

- **配布バイナリを落とす**（既定）— ビルドはしません
- **この端末でビルドする** — ダウンロードはしません
- **落とす → 駄目ならビルドする**

ビルドは空きディスク 8GB 以上を要し、CPU とメモリを大きく使います。**メモリが少ない環境
（Raspberry Pi など）では、スワップを使い切ってシステムごと落ちることがあります。**
コンパイル中も全機能を使えます。Windows でビルドする場合は Visual Studio のビルドツール
（リンカ）が別途必要です。

進捗は同じ画面に出ます（ビルド中の経過時間、cargo の最新行、成功・失敗、途中で止まった
場合はその旨）。生ログは `bin/fast-mode-build.log` に在ります。

### 取得が始まらないとき

web バンドルが古い・同梱外の拡張が在る等、**この端末側の状態**が原因で高速モードを断った
場合は、バイナリを取り直しても解決しないため、ダウンロードもビルドも行いません。その理由
も同じ画面に出ます。
