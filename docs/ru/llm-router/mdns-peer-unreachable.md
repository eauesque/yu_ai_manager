# mDNS-бэкенд остаётся в состоянии «недоступен»

Причины, диагностика и устранение ситуации, когда бэкенд, добавленный через
автообнаружение mDNS в LLM Router, остаётся в состоянии
«недоступен (unreachable)» и не восстанавливается.

---

## Обзор структуры

```
MdnsService (zeroconf layer)
  └─ on_peer_added / on_peer_updated / on_peer_removed
       └─ LlmRouterMdnsBridge
            ├─ _verify()       ← HTTP-проверка через /api/mdns/identity
            ├─ _apply_peer_to_catalog()  ← Регистрация в BackendCatalog
            ├─ _enter_cooldown() / _in_cooldown()  ← Ограничение повторов после ошибки
            └─ retry_pending_peers()  ← Sweep каждые 60 с (с v4.91.15)
```

**Важный поток**:

1. zeroconf обнаруживает пир → вызывается `on_peer_added`
2. `_verify()` обращается к `/api/mdns/identity` и проверяет `node_id` и `product`
3. Успех → `_apply_peer_to_catalog()` добавляет бэкенд в каталог
4. Ошибка → переходит в cooldown на 60 с; события с тем же `node_id` игнорируются
5. **С v4.91.15**: задача sweep каждые 60 с повторяет проверку ожидающих пиров после истечения cooldown

---

## Частые сценарии перехода в состояние «недоступен»

### Сценарий A — Первая проверка verify завершилась ошибкой → тишина из-за cooldown

**Симптом**: Бэкенд отображается в LLM Router, но status=unreachable.  
**Причина**:
- HTTP-сервер удалённого узла ещё не был готов сразу после запуска
- Собственный порт изменился, а пир ссылался на старую TXT-запись (ошибка переопределения `--port` до v4.91.14: исправлено в 35a3679a)

**Поведение (до v4.91.14)**: После истечения cooldown (60 с) ожидается следующее событие `on_peer_updated`; если оно не наступит, восстановление не произойдёт никогда.

**Поведение (с v4.91.15)**: После истечения cooldown следующий тик sweep (не более чем через 60 с) автоматически повторяет попытку → при успехе каталог обновляется.

---

### Сценарий B — zeroconf не генерирует `ServiceStateChange.Updated`

**Симптом**: Пир перезапустился, но LLM Router показывает прежний статус.  
**Причина**: В зависимости от состояния кэша zeroconf, изменение TXT может не вызывать событие `Updated` (известное поведение библиотеки zeroconf).  
**Решение**: Задача sweep из v4.91.15 обнаруживает это в течение 60 с.

---

### Сценарий C — Порт удалённого узла не совпадает с объявленным значением

**Симптом**: curl достигает пира, но таймауты verify продолжаются.  
**Причина**: Используется флаг `--port` в CLI, но `server.port` в config.json содержит старое значение → в TXT mDNS объявляется неверный порт.  
**Исправление**: Устранено в v4.91.14 (35a3679a): `config["server"]["port"]` перезаписывается фактическим портом. Если старый скрипт запуска напрямую изменяет config.json, проверьте и этот файл.

---

### Сценарий D — Не зарегистрирован в trusted_peer_registry

**Симптом**: LLM Router показывает «ready», но прокси к `/ext/<name>/v1/*` возвращает 403.  
**Причина**: Verify прошёл успешно и пир попал в каталог, но процесс перезапустился до вызова `_apply_peer_to_catalog()`, либо `service_kind != "yu"` привело к пропуску регистрации в registry (bare Ollama-пиры не регистрируются по замыслу).  
**Проверка**:
```bash
curl -s http://127.0.0.1:PORT/api/mdns/peers | python3 -m json.tool | grep -E 'node_id|trusted'
```

## Шаги диагностики

### 1. Проверить текущее состояние пира

```bash
# Список известных пиров
curl -s http://127.0.0.1:PORT/api/mdns/peers | python3 -m json.tool

# Список бэкендов LLM Router (записи mDNS имеют псевдоним с префиксом "mdns-")
curl -s http://127.0.0.1:PORT/api/llm_router/status | python3 -m json.tool
```

### 2. Убедиться, что удалённый узел достигает собственного endpoint identity

На удалённом узле:
```bash
curl -v http://<собственный-LAN-IP>:<PORT>/api/mdns/identity
```

Ожидаемый ответ:
```json
{"product": "yu_ai_manager", "node_id": "...", "version": "..."}
```

При ошибке:
- Проблема с брандмауэром или маршрутизацией
- Фактический порт не совпадает с объявленным (проверить, используется ли `--port` при запуске)

### 3. Проверить объявленный порт

```bash
# Лог запуска содержит "web_port"
grep -i "web_port\|mdns.*port\|effective_port" logs/app.log | tail -20

# Или через API settings
curl -s http://127.0.0.1:PORT/api/server/info | python3 -m json.tool | grep port
```

### 4. Проверить состояние cooldown

GUI: **LLM Router** > карточка бэкенда > Детали показывает `last_error` и `last_seen_at`.
Если ошибка «identity verification failed» — пир достижим, но содержимое не совпадает (конфликт node_id / product). Если «timeout» — HTTP не достигает пира.

### 5. Проверить логи sweep

```bash
grep "\[mdns\] sweep" logs/app.log
```

`sweep re-verified peer <8символов>` означает, что sweep выполнил восстановление.

## Ручное восстановление

Если не хочется ждать следующего тика sweep:

### Способ 1: Перезапустить удалённый узел

При перезапуске zeroconf генерирует `ServiceStateChange.Removed` + `Added` →
`on_peer_removed` сбрасывает cooldown → `on_peer_added` немедленно выполняет повторную проверку.

### Способ 2: Перезапустить сервис mDNS через интерфейс настроек

**Настройки** > **LLM Router** > кнопка **Перезапустить mDNS** (если доступна).

### Способ 3: Перезапустить приложение

Cooldown существует только в памяти. Перезапуск сбрасывает все cooldown
и сразу после запуска повторно проверяет все пиры.

## Меры профилактики

| Проверка | Метод |
|---|---|
| При использовании `--port`: совпадает ли `server.port` в config.json? | Проверить config.json |
| Разрешён ли входящий трафик на `PORT` в брандмауэре? | `sudo ufw status` / Настройки macOS |
| В среде с несколькими NIC: выполняется ли bind на нужный LAN-интерфейс? | `mdns.bind_address` в config.json |
| Используется ли v4.91.15 или выше (с задачей sweep)? | `curl .../api/server/info` |
