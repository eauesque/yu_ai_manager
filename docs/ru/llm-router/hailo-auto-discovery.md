# Автоматическое обнаружение Hailo LLM

**Поддерживаемая версия**: v4.66.0 и выше

## Обзор

yu_ai_manager может автоматически обнаруживать и использовать конечные точки LLM, работающие на Hailo NPU Pi5, без изменения `config.json`. Просто подключите Pi5 к локальной сети, и другие узлы yu_ai_manager смогут вызывать Hailo LLM.

## Два типа конечных точек

| Конечная точка | Описание | Стандартный шаблон URL |
|---|---|---|
| **yu extension Hailo LLM** | LLM, совместимый с OpenAI, предоставляемый встроенным расширением `builtin-hailo-genai` в yu_ai_manager | `http://<host>:<yu-port>/ext/hailo-genai/v1/` |
| **hailo-ollama** | LLM, совместимый с OpenAI, предоставляемый внешним двоичным файлом `/usr/bin/hailo-ollama` (порт по умолчанию `:8000`) | `http://<host>:8000/v1/` |

Оба могут работать одновременно и оба регистрируются автоматически. С HailoRT 5.3.0+ и установленным `HAILO_OLLAMA_VDEVICE_GROUP_ID=YU_SHARED`, планировщик HailoRT передает физическое устройство в режиме round-robin, поэтому конфликтов при одновременном использовании обоих нет.

## Локальная автоматическая регистрация (Phase A)

При запуске yu_ai_manager независимо обнаруживает следующие две конечные точки:

1. **yu extension**: Если `hailo_platform.genai.LLM` импортируется и существует `/dev/hailo0` или `/dev/h1x-0`, он автоматически регистрируется как backend `hailo-local` в каталоге
   (v4.66.1 добавила поддержку Raspberry Pi 5 + AI HAT + HailoRT 5.3.0, который экспортирует устройство как `/dev/h1x-0`)
2. **hailo-ollama**: HTTP зонд отправляется на `localhost:8000/v1/models` (timeout 2 секунды). Если получен ответ 200, он автоматически регистрируется как backend `hailo-ollama-local`

Если backend с тем же alias уже существует в `llm_router.backends` в `config.json`, эта конфигурация имеет приоритет (не будет перезаписана).

## Реклама mDNS (Phase B)

На основе результатов обнаружения Phase A, yu_ai_manager объявляет возможности Hailo другим узлам через TXT записи mDNS:

- `capabilities=llm,hailo` -- Указывает, что расширение yu доступно
- `hailo_ollama_url=http://192.168.1.10:8000/v1/` -- Включено только если работает hailo-ollama (переписано на IP доступный из LAN)

Когда другие узлы yu_ai_manager получают это через mDNS, они выполняют проверку идентичности через конечную точку `/api/mdns/identity`, а затем автоматически регистрируют дополнительные backends с следующими aliases:

- `mdns-<node_id[:8]>-hailo` -- yu extension Hailo LLM (когда `capabilities` включает `hailo`, URL получен из `web_port` соседа + адреса)
- `mdns-<node_id[:8]>-hailo-ollama` -- Внешний hailo-ollama (когда `hailo_ollama_url` объявляется, URL из TXT записи используется как есть)

## Конфигурация

Включено по умолчанию. Вы можете отключить это в `config.json` следующим образом:

```json
{
  "llm_router": {
    "hailo_ollama": {
      "enabled": false,
      "port": 8000
    }
  }
}
```

- **`enabled`**: Установите на `false` для полного отключения автоматического обнаружения hailo-ollama. Обнаружение расширения yu контролируется отдельно (определяется автоматически по доступности расширения)
- **`port`**: Номер порта для hailo-ollama (по умолчанию 8000). Значения вне диапазона 1--65535 возвращаются к умолчанию с предупреждением в логе

## Примечания по безопасности

**hailo-ollama не имеет аутентификации**. При объявлении через mDNS, **любой узел в LAN может свободно потреблять вычислительные ресурсы hailo-ollama**.

| Конечная точка | Аутентификация | Эффективное открытие LAN |
|---|---|---|
| yu extension (`/ext/hailo-genai/v1/`) | Цепь веб-аутентификации yu (PIN/сессия/ключ API) | Только клиенты, аутентифицированные в yu |
| hailo-ollama (`hailo_ollama_url`) | **Нет** | **Все узлы в LAN** |

Для окружений, отличающихся от домашних локальных сетей или доверенных VLAN (например, открытый Wi-Fi), отключите автоматическое объявление с `hailo_ollama.enabled: false`.

## Внешний вид в WebUI LLM Router

Автоматически зарегистрированные backends отображаются на панели управления `/llm-router` (v4.65.0):

- `hailo-local` / `hailo-ollama-local` -- Локально обнаруженные (источник: значок `static`)
- `mdns-<id>-hailo` / `mdns-<id>-hailo-ollama` -- Обнаруженные через mDNS (источник: значок `mdns`)

Все могут быть временно отключены через переключатель Disable. Отключенное состояние сохраняется в `data/llm_router_state.json` и сохраняется после перезагрузок (реализовано в v4.65.0).

## Защита от ложных срабатываний

Обнаружение Phase A имеет два механизма защиты:

1. **Избежание самозондирования**: Если `hailo_ollama.port` установлен на то же значение, что и собственный веб-порт yu, зонд полностью пропускается (предотвращает неправильное определение yu как hailo-ollama)
2. **Приоритет существующего backend**: Если backend с тем же `localhost:<port>/v1` уже зарегистрирован в `config.json`, зонд пропускается для соблюдения намерения пользователя

## v4.66.2 -- Аутентификация доверенного peer (исправление реальной дыры в аутентификации устройства)

В автоматическом обнаружении Hailo v4.66.0, расширение `/ext/hailo-genai/*` yu было защищено цепью веб-аутентификации. Когда драйвер LLM Router (который не имеет ни Bearer токена, ни сессии) пытался зондировать/отправлять, middleware аутентификации возвращал honeypot HTML, вызывая ошибки парсинга JSON и backend оставался застрявшим как `unreachable`.

### Как это работает

- Новый `TrustedPeerRegistry` инициализирует `127.0.0.1` / `::1` при запуске
- Когда `LlmRouterMdnsBridge` успешно проверяет peer (HTTP GET к `/api/mdns/identity` + подтверждение совпадения node_id), все объявленные адреса этого peer добавляются в реестр
- `auth_chain.check_trusted_peer` пропускает аутентификацию PIN при получении запроса для путей `/ext/<name>/v1/*`, если remote_addr находится в реестре
- Существующие пути аутентификации ключа API / сессии / cookie остаются неизменными

### Связь с Quick Lock

- **loopback** (самозондирование yu): Всегда проходит, даже во время quick_lock
- **peer IP**: Запросы отклоняются во время quick_lock (`check_quick_lock` возвращает 503). Это означает, что peers также уважают состояние "пользователь намеренно заблокировал"

Это позволяет следующим сценариям работать как ожидается:

- Самозондирование `hailo-local` pi2 (`http://localhost:5000/ext/hailo-genai/v1/models`)
- Кросс-узловая отправка из Windows на `mdns-<id>-hailo` pi2 (`http://192.168.50.4:5000/ext/hailo-genai/v1/chat/completions`)

### Конфигурация

Не требуется изменение файла конфигурации. Даже в окружениях, где mDNS отключен, инициализация loopback все еще работает, поэтому исправление самозондирования доступно безусловно.

### Отладка

Установите переменную окружения `TAGDB_DEBUG_TRUSTED_PEERS=1` перед запуском yu, чтобы добавить поле `trusted_ips` в ответ `/api/mdns/peers`. Не устанавливайте это в production (список доверия по сути является "списком целей атак" и не должен быть открыт на неаутентифицированных конечных точках).

### Граница безопасности

Работает под предположением "доверенной LAN" (то же предположение, что и в Phase B v4.64.0). Защита от вредоносных узлов с физическим доступом к LAN выходит за рамки -- используйте переключатель Disable в WebUI `/llm-router` или quick_lock для таких случаев.

Смотрите `docs/superpowers/specs/2026-04-09-trusted-peer-auth-design.md` для деталей.
