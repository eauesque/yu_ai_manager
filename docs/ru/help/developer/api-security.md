# Рекомендации по безопасности API

Используйте этот документ при добавлении или изменении конечной точки API.

## Первое решение

Каждая конечная точка должна быть классифицирована заранее как одна из следующих:

- `public`
- `session/user`
- `admin`
- `localhost-only`

Если вы не уверены, выберите `admin`.

## Основные правила

1. Не предполагайте, что `GET` безопасен.
2. `read-only API keys` предназначены только для простого чтения.
3. Внутренние пути, инвентари, история, контент, логи и результаты анализа - это `admin`.
4. Проверки localhost должны использовать помощники, осознающие прокси.
5. Конечные точки конфигурации требуют списков разрешений и строгой проверки.
6. Секреты должны быть зашифрованы и скрыты через общих помощников.

## Небезопасно для ключей только для чтения

- внутренние пути
- инвентари ID файлов/членов
- подсказки, аннотации, транскрипции, логи чата
- результаты OCR / анализа
- очередь, история, аудит, одобрение, планировщик, состояние ошибки сканирования
- состояние бэкенда расширения / профиля / резервной копии / вебхука / секрета
- результаты, полученные с сохраненными сторонними учетными данными

## Проверки localhost

Не используйте напрямую:

```
request.remote_addr == "127.0.0.1"
```

Используйте существующих помощников:

- `get_client_ip()`
- `is_local_request()`
- `is_loopback_request()`

## Правила конечной точки конфигурации

Обязательно:

- список разрешений ключей
- строгая проверка типов
- проверка диапазона / перечисления / URL
- скрытие секреты при чтении
- зашифрованное хранилище для секретов

Запрещено:

- слепое `config.update(...)`
- `bool(value)` для булевых значений запроса
- универсальные слияния, которые обходят обработку секретов

## Секреты

- никогда не возвращайте текущие значения секреты
- никогда не включайте токены/заголовки/блоб-секреты в конечные точки списка
- никогда не перезаписывайте существующие секреты замаскированными заполнителями
- всегда используйте выделенное хранилище или общего помощника

## Исходящие запросы из API

Не делайте восходящие зонды или выборку обнаружения из конечных точек `GET`.

Если неизбежно:

- требует `admin`
- держите таймауты короткими
- блокируйте localhost / приватный IP / цели метаданных

## Минимальные тесты

Для чувствительных конечных точек добавьте:

1. `read-only key -> 403`
2. `admin key -> 200`
3. `invalid input -> 400`
4. проверки скрытия секреты
5. регрессионные тесты localhost, осознающие прокси, где уместно

## Контрольный список проверки

- Действительно ли этот `GET` безопасен для публичного доступа / доступа только для чтения?
- Он раскрывает пути, инвентари, подсказки, транскрипции, историю или необработанные метаданные?
- Он утекает секреты?
- Использует ли он помощников, осознающих прокси?
- Избегает ли он неявного приведения логических значений?
- Избегает ли он слепого слияния конфигурации?
- Избегает ли он непредусмотренных исходящих запросов?
- Включает ли он регрессионные тесты области администратора?

Политика по умолчанию: начните узко, затем откройте намеренно только при необходимости.
