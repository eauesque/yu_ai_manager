# Руководство по настройке производительности

Руководство по тонкой настройке YU AI Manager для комфортной работы с библиотеками от 100 тыс. файлов.
Многие оптимизации работают автоматически, но дополнительная настройка под конкретное окружение может улучшить результаты.

---

## 1. Рекомендуемое оборудование

| Параметр | Минимум | Рекомендуется (100 тыс.+) |
|----------|---------|--------------------------|
| CPU | 2 ядра | 4+ ядра (параллельная генерация миниатюр) |
| RAM | 4 ГБ | 8+ ГБ |
| Хранилище | HDD | **Настоятельно рекомендуется SSD** — напрямую влияет на скорость ответа БД |
| Сеть | — | 1 Гбит/с+ при LAN-доступе |

**Особенно важно**: Файл базы данных (`data/tags.db`) **должен** находиться на SSD.
Изображения могут храниться на HDD, но БД на HDD значительно замедляет поиск и просмотр.

---

## 2. Оптимизация первичного сканирования

### Сканирование в реальном времени

Поиск и просмотр миниатюр работают в штатном режиме и во время сканирования.
Внутренне используется read-only соединение с БД, не конкурирующее со записью при сканировании.

### Автооптимизация после сканирования

При завершении сканирования автоматически обновляется статистика БД (ANALYZE).
Это оптимизирует план выполнения поисковых запросов.

---

## 3. Улучшение скорости просмотра

### Кэш Service Worker

| Тип | Лимит кэша | Эффект |
|-----|-----------|--------|
| Миниатюры | 5 000 штук | Мгновенное отображение сетки повторно |
| Превью (1200px) | 200 штук | Ускорение открытия модального окна |
| Оригиналы | 50 штук | Мгновенное повторное отображение |

### Виртуальный скролл

**Включение**: Settings > Appearance > «Virtual Scroll» ON

Виртуальный скролл рендерит в DOM только карточки в видимой области — значительно снижает нагрузку на память и отрисовку.
Настоятельно рекомендуется для библиотек от десятков тысяч файлов.

### Миниатюры WebP

Миниатюры генерируются в формате WebP (на 30–40% меньше JPEG).
Применяется автоматически.

---

## 4. Производительность поиска

### Индексы

В БД автоматически создаются индексы, оптимизированные для основных паттернов поиска.

**Ориентировочные значения**:
- Поиск без фильтров: В пределах 50 мс даже для 280 тыс. файлов
- Поиск с фильтром тегов: В пределах 100 мс
- Поиск по пути (FTS5): В пределах 50 мс

### FTS5 vs LIKE

FTS5 (Full-Text Search) используется автоматически — в 20–100 раз быстрее традиционного LIKE.

**Примечание по японскому поиску**: Поиск с иероглифами/хираганой/катаканой может внутренне использовать LIKE-поиск — это нормальное поведение (ограничение токенизатора SQLite FTS5).

---

## 5. Оптимизация воспроизведения видео

### Кэш faststart

| Параметр | Значение |
|----------|---------|
| Расположение кэша | `cache/faststart/` |
| Лимит | 4 ГБ (LRU) |
| Поддерживаемые | MP4, MOV |

**Ориентировочные улучшения**:

| Размер файла | Без faststart | С faststart |
|-------------|--------------|------------|
| 5–50 МБ | 2–10 сек | ~200 мс |
| 50–200 МБ | 10–60 сек | ~500 мс |
| 200–500 МБ | Несколько минут | ~1 сек |

FFmpeg обязателен для faststart.

---

## 6. Управление использованием памяти

### SQLite mmap

Для больших БД (100 тыс.+) автоматически устанавливается mmap в 1 ГБ.

### Управление вкладками браузера

YU AI Manager обменивается данными с каждой вкладкой по SSE.

- Максимум 10 одновременных SSE-соединений с одного IP
- Закрытие лишних вкладок освобождает ресурсы

**Рекомендация**: Не открывать более 3–4 вкладок одновременно.

---

## 7. Чеклист «почему медленно»

### Базовая проверка

- [ ] **Используется SSD**: `data/tags.db` на HDD замедляет все операции
- [ ] **FFmpeg установлен**: Обязателен для ускорения видео
- [ ] **Количество вкладок браузера**: Проверить, не открыто ли более 5

### Медленный просмотр

- [ ] **Включить виртуальный скролл**: Settings > Appearance > Virtual Scroll
- [ ] **Не очищать кэш браузера**: Кэш Service Worker должен работать

### Медленный поиск

- [ ] **Завершить сканирование**: ANALYZE выполняется при завершении сканирования

### Медленное воспроизведение видео

- [ ] **Проверить FFmpeg**: `ffmpeg -version`

## 8. Ориентировочные показатели производительности

| Операция | 280 тыс. файлов | 100 тыс. файлов |
|---------|-----------------|-----------------|
| Отображение сетки (первый раз) | 200–500 мс | 100–300 мс |
| Отображение сетки (с кэшем) | < 50 мс | < 50 мс |
| Поиск по тегам | < 100 мс | < 50 мс |
| Поиск по пути (FTS5) | < 50 мс | < 30 мс |
| Миниатюра (кэш-хит) | < 5 мс | < 5 мс |
| Начало воспроизведения видео (faststart) | 200 мс | 200 мс |

## Быстрый режим (сервер Rust)

В поддерживаемых средах запуск автоматически переключается на сервер Rust (`yu-server`).

В настройках «Сервер» -> «Быстрый режим» выбирается **способ получения**:

- **Скачать опубликованный бинарный файл** (по умолчанию) -- никогда не собирает
- **Собрать на этом устройстве** -- никогда не скачивает
- **Скачать, а при неудаче собрать**

Сборка требует не менее 8 ГБ свободного места и активно использует процессор и память. **На устройствах с малым объёмом памяти (например, Raspberry Pi) она может исчерпать подкачку и уронить всю систему.** Во время компиляции все функции остаются доступными. Для сборки в Windows дополнительно нужны инструменты сборки Visual Studio (компоновщик).

Ход показан на том же экране: прошедшее время, последняя строка cargo, успех или неудача, а также если сборка прервалась на середине. Полный журнал — `bin/fast-mode-build.log`.

Если быстрый режим отклонён из-за состояния самой копии (устаревший веб-бандл, расширение вне поставляемого списка), получение бинарного файла ответа не изменит: ни загрузка, ни сборка не выполняются. Эта причина также показана там.
