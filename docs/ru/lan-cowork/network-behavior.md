# LAN Cowork сетевое поведение (что происходит в LAN)

> Целевая версия: v4.538.0 и выше Rust standalone (`yu-server`). О конфигурации гибридного режима с Python
> бэкэндом см. раздел «Отличия от Python версии» в конце этой страницы.

На этой странице собрана информация о том, **«что начинает делать ваше устройство в сети при включении LAN Cowork»**.
Прочитайте эту страницу перед изменением параметров.

---

## Основные моменты

- **По умолчанию ничего не происходит.** Rust standalone не выполняет ни прослушивание, ни объявление в LAN
  до тех пор, пока вы явно не включите его в описанных ниже параметрах.
- При включении система **становится видима для других узлов в одной LAN**. Это запланированное поведение.
- **Наличие или отсутствие PIN не влияет на объявление обнаружения.** Подробнее см. раздел «Связь с PIN (легко неправильно понять)».

---

## Что начинает происходить при включении

| Поведение | Описание |
|---|---|
| **UDP прослушивание** | Привязывает `0.0.0.0:19850` (все интерфейсы) |
| **Периодическое объявление** | Каждые 10 секунд отправляет подписанный HELLO на `255.255.255.255:19850`. Содержимое включает ID узла, открытый ключ, порт API, имя хоста и т.д. |
| **Регистрация других узлов** | Проверяет подпись полученных HELLO и добавляет удаленный узел в список пиров (TOFU) |
| **Входящие HTTP запросы** | Конечные точки для пиров (см. таблицу ниже) начинают возвращать ответы |
| **Локальная доставка** | Передает принятые события от пиров на SSE (`/api/events/stream`), который слушают авторизованные клиенты |
| **Очистка устаревших данных** | Каждые 60 секунд удаляет из памяти истекшие запросы на спаривание и открытые PIN-коды |

### Входящие конечные точки

| Конечная точка | Аутентификация |
|---|---|
| `GET /ext/lan_cowork/api/peer/discover` | **Сеанс не требуется** (получение списка пиров) |
| `GET /ext/lan_cowork/api/peer/status` | **Сеанс не требуется** (дескриптор узла) |
| `POST /ext/lan_cowork/api/peer/register` | **Сеанс не требуется** (самостоятельная регистрация пира. Проверка места регистрации выполняется на сервере) |
| `POST /ext/lan_cowork/api/peer/pair/request` / `pair/verify` | **Сеанс не требуется** (начало спаривания. Непарные узлы не могут иметь сеанс) |
| `POST /ext/lan_cowork/api/peer/token/renew` | Подпись + nonce (Bearer не требуется) |
| `POST /ext/lan_cowork/api/peer/event` / `heartbeat` | Подпись + Bearer токен |

«Сеанс не требуется» означает **не требуется вход в систему**, а не **отсутствует аутентификация**.
Поскольку непарные узлы не могут иметь сеанс входа, эти 5 маршрутов открыты как исключение.
Для всех остальных маршрутов требуется вход в систему как обычно.

## Как включить и отключить

Переключается в **`extensions` секции** файла `config.json`.

```json
{
  "extensions": {
    "builtin-lan-cowork": {
      "enabled": true
    }
  }
}
```

- **Если ключ отсутствует, функция отключена** (Rust standalone).
- Требуется **перезагрузка** для вступления в силу.
- Если требуется временное переключение, можно задать опцию при запуске. Приоритет следующий:
  **командная строка > `config.json` > переменная окружения > умолчание**.

| Способ | Включить | Отключить |
|---|---|---|
| Командная строка | `--native-daemon` | `--no-native-daemon` |
| Переменная окружения | `YU_LAN_COWORK_NATIVE_DAEMON=1` | То же `=0` |

> Переменная окружения интерпретирует только `1`, `true` или `yes` как «включено». `on` и `Y` **рассматриваются как отключено**.

### Проверка включения

```bash
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5000/ext/lan_cowork/api/peer/status
```

| Ответ | Значение |
|---|---|
| `200` | Включено. Функция пира работает |
| `405` | **Отключено** (функция вообще не встроена) |
| `503` | Включено, но не готово (ключ узла ещё не сгенерирован или внутренняя инициализация не удалась) |

> **На отображение списка расширений в интерфейсе нельзя полагаться.** В списке расширений LAN Cowork может
> отображаться как «включено», но это основано на информации, встроенной в доставку, и **отличается от того,
> действительно ли работает фоновый демон**. Проверку следует выполнять по ответу конечной точки выше или по
> строке `native_daemon=...` в журнале запуска.

## Связь с PIN (легко неправильно понять)

**Неправильно считать, что без установленного PIN ничто в LAN не сможет коснуться системы.**

- **Правильно**: Использование `--lan` (прослушивание на всех интерфейсах) требует PIN, и без него запуск будет остановлен.
  Прослушивание по умолчанию — это `127.0.0.1`, поэтому **при нормальном запуске HTTP не доступен из LAN**.
- **Примечание 1**: Если вы напрямую задали IP адрес LAN в параметре `--host`, эта обязательная проверка PIN не срабатывает.
  Кроме того, без PIN установлены врата входа в систему, поэтому **избегайте открытия LAN без PIN**.
- **Примечание 2**: **UDP-объявление не зависит от наличия PIN.** При включении даже узел без PIN
  объявляет о своём существовании в LAN каждые 10 секунд. PIN ограничивает только экспозицию HTTP.

Другими словами, **PIN ограничивает экспозицию HTTP, но не останавливает объявление обнаружения.**

### При прослушивании только loopback (v4.539.0 и новее)

Если адрес прослушивания только loopback (по умолчанию `127.0.0.1`, это также относится к настольной версии),
**этот узел не объявляет себя в LAN**. Другие узлы не смогли бы подключиться, даже если бы он объявлялся.
После запуска один раз записывается следующее предупреждение (это WARN, а не INFO, поэтому оно видно по умолчанию).

```
LAN Cowork discovery inactive: server listens on loopback only; bind a LAN address or use --lan
```

Чтобы использовать его в LAN, привяжите LAN-адрес или используйте `--lan` (`--lan` требует PIN).

> До v4.539.0 слушатель только loopback объявлял LAN IP. Пиры могли его обнаружить,
> но не подключиться; поэтому это поведение было изменено.

## Что нужно знать перед включением

- **Отключение не удаляет автоматически записи о пирах, которые были записаны при включении.** Кроме того,
  **при первом запуске после включения** выполняется очистка старых записей о пирах
  (удаляются записи, для которых в течение 7 дней или более не было успешного подключения, и непарные записи, которые существуют более 1 часа).
  Рекомендуется создать резервную копию `tags.db` перед переключением.
- События пиров, полученные от других узлов, передаются на SSE (`/api/events/stream`), который слушают авторизованные клиенты.
  **Содержимое — это входные данные от удаленного узла**
  (ID отправителя заменяется на проверенное значение на сервере).
- В журнале записываются **только количество, тип и ID отправителя**,
  содержимое события не регистрируется.
- Если вы хотите проверить статус работы, включите уровень логирования INFO
  (например: `RUST_LOG=yu_server=info`). При параметрах по умолчанию строки, указывающие на получение событий пира, не выводятся.

## Отличия от Python версии

| | Python бэкэнд в гибридном режиме | Rust standalone |
|---|---|---|
| По умолчанию | **Включено** (если в `config.json` нет этого пункта, функция включена) | **Отключено** (требуется явное включение) |
| Реализация | Обработка Python расширением | Обработка `yu-server` |

**Rust standalone намеренно устанавливает «отключено по умолчанию».** Это сделано, чтобы избежать изменения поведения сети при обновлении. Поведение гибридной конфигурации с Python не изменилось.

> В старой документации конфигурация включения описывалась как `{"lan_cowork": {"enabled": true}}` (верхний уровень),
> **но этот ключ в этой позиции не читается ни одной реализацией.** Правильная позиция — это
> раздел `extensions`, описанный выше.
