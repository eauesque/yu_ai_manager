# Справочник по обслуживанию тестов

Руководство по ключевым моментам, когда pytest зависает из-за устаревшей инфраструктуры тестирования или зависимостей окружения.

## Назначение

- Различать между `failed` и `skipped` тестами
- Дифференцировать между обычными пропусками, зависящими от окружения, и устаревшими тестами, требующими ремонта
- Установить фиксированный кратчайший путь, когда широкий запуск (`pytest tests -q --maxfail=1`) зависает

## Основные команды

Обычная полная проверка:

```powershell
venv\Scripts\python.exe -m pytest tests -q --maxfail=1
```

Также проверьте причины пропусков:

```powershell
venv\Scripts\python.exe -m pytest tests -q -rs
```

Обращайтесь с общим тестовым сервером строго:

```powershell
$env:PYTEST_STRICT_AUTOSTART_SERVER="1"
venv\Scripts\python.exe -m pytest tests\api -q
```

Аудит лицензии:

```powershell
venv\Scripts\python.exe scripts\license_audit.py
```

## Чтение текущих пропусков

По состоянию на 2026-04-21 широкие запуски показывают, что причины пропусков сконцентрированы в этих 5 основных категориях.

### 1. Общий тестовый сервер не запущен

Наиболее частый пропуск. Общий сервер в `tests/conftest.py` использует запуск наилучшего усилия, и если запуск не удается, группы, зависящие от браузера/сервера, переходят на пропуск, а не на сбой.

Представительные причины:

- `Shared test server unavailable on port <PORT>`

Основные цели:

- `tests/api/`
- Наборы тестов просмотра пользовательского интерфейса браузера
- Тесты LAN Cowork / Fleet, зависящие от браузера/сервера
- Живые тесты браузера, использующие `TARGET_URL` / `BASE` / `TARGET`
- Тесты аудита, использующие пользовательские приспособления Playwright/WebKit вместо приспособления `page`

При обычном запуске это **нормальный пропуск**. Однако исследуйте, если:

- Модульные тесты, не связанные с общим сервером, также пропускаются по той же причине
- Ранее прошедшие тесты общего сервера внезапно начинают пропускаться в больших количествах
- Причина неясна даже с `PYTEST_STRICT_AUTOSTART_SERVER=1`

### 2. Тесты, специфичные для ОС

Тесты, специфичные для Linux, с изоляцией песочницы / AppArmor / изоляцией процесса. Пропуск правильный на Windows.

Представительные примеры:

- `tests/basic/test_os_isolation.py`
- `tests/test_process_isolation_integration.py`

Представительные причины:

- `Linux only`
- `AppArmor is Linux-specific`

Это **нормальный пропуск**.

### 3. Необязательные зависимости и отсутствующие внешние компоненты

Тесты, которые не запускаются в окружениях без определенных пакетов или внешних узлов.

Представительные примеры:

- mDNS реальное оборудование E2E: `optional zeroconf package is not installed`
- Запуск браузера: `Playwright unavailable`, `launch failed`
- ONNX / YAML / ComfyUI / внешние узлы логического вывода не подключены

Это **нормальный пропуск**. Это не цель ремонта — окружению просто не хватает предварительных условий.

### 4. Недостаточные тестовые данные

Тесты браузера, требующие изображений, результатов поиска, логов разговоров или нескольких элементов данных, которые не могут работать с облегченной БД, пропускаются.

Представительные причины:

- `No search results available in database`
- `Skipped because no images in DB`
- `2 or more files required`
- `No prompts to test copy`

Это **обычно нормальный пропуск**. Однако если приспособление должно предоставлять необходимые данные, подозревайте устаревание.

### 5. Ограничение скорости и защита внешнего API

Некоторые интеграционные тесты уважают внешние сервисы или пределы скорости, пропуская их.

Представительные причины:

- `Skipped due to rate limit`

Это **нормальный пропуск**.

### 6. Долгоживущие тесты Fuzz / Burn-in

Burn-in под `tests/fuzz/` предназначен для проверки долговечности и устойчивости к сбоям, а не для маршрутного регрессионного тестирования.

Исключено по умолчанию через паттерн маркера в `pytest.ini`.

Для запуска:

```powershell
venv\Scripts\python.exe -m pytest tests\fuzz -q -m fuzz
```

По желанию:

```powershell
$env:FUZZ_DURATION="60"
venv\Scripts\python.exe -m pytest tests\fuzz\test_api_fuzz.py -q -m fuzz
```

Это **не смешивается в обычные широкие запуски**.

## Паттерны, требующие исследования

Следующее не следует отклонять как "пропуск в порядке", но рассматриваться как цель обслуживания тестов.

### A. Ранее прошедшие легкие тесты отказывают в пропуске установки

Примеры:

- API дымовые тесты на основе приспособлений app/client, которые должны быть самостоятельными, помещаются в предварительные условия общего сервера
- Тесты миграции / схемы / вспомогательного ПО БД отказывают из-за инициализации глобального состояния во время выполнения

Подозревайте несоответствие тестового оборудования и предположения реализации.

### B. Широкий запуск проходит, но одиночные запуски не удаются

Типичные причины:

- Зависит от состояния глобального процесса
- Случайная зависимость от побочных эффектов, инициализированных ранее во время широкого запуска

Восстановите одиночные запуски в воспроизводимое состояние.

### C. Неясные причины пропусков

Плохие примеры:

- `failed`
- `not ready`
- `something wrong`

Причины пропусков должны быть краткими изложениями, объясняющими, что отсутствовало и вызвало пропуск.

## Приоритет ремонта

1. Исправить жесткие сбои, которые блокируют широкие запуски
2. Исправить устаревшие тесты, которые разбиваются только на одиночных запусках
3. Переместить пропуски, зависящие от браузера/сервера, к безопасным пропускам, а не к сбоям
4. Поддерживать необязательные пропуски для необязательных зависимостей и тестов, специфичных для оборудования

## Что было исправлено при этой очистке

- Унифицированы тесты браузера/сервера для безопасного пропуска при недоступности общего сервера, а не для отказа
- Аудит лицензии теперь проверяет только объявленные зависимости `requirements*.txt`, а не весь venv
- Тестовая БД отвечает предварительным условиям пути FTS текущей схемы поиска
- Миграции 54 / 55 теперь надежны для эволюции схемы и неинициализированного состояния во время выполнения

## Руководство по решениям в случае сомнений

- Отсутствующие предварительные условия окружения → пропуск уместен
- Устаревшие ожидания, не соответствующие текущей реализации → исправьте тест
- Побочные эффекты широкого запуска в зависимостях → исправьте реализацию или тест
- Модульный тест, требующий состояния глобального процесса → поставить под вопрос дизайн
