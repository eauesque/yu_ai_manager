# Исправление диагноза «CMA не освобождается» в HailoRT / driver 5.4.0: протокол проверки

Создано: 2026-08-16 / Последнее обновление: 2026-08-17 / Соответствующая версия: yu_ai_manager 4.623.1

Запись о проверке гипотезы и A/B-тестировании официальной vanilla-версии и версии с исправлением `FOLL_LONGTERM` на `hailo-ai/hailort-drivers` v5.4.0 (опубликовано 2026-08-16, GPL-2.0, исходный код открыт) в отношении события, ранее диагностированного как утечка (не освобождение) CMA (см. `docs/development/development_docs/HAILO_FORUM_FOLLOWUP_CMA_INFERENCE_LEAK.md`), и об исправлении ошибочного диагноза на стороне измерения.

---

## 1. Заключение

**Итоговая повторная проверка от 2026-08-17 (4-й заход): вердикт `VERDICT: FAIL`, действовавший вплоть до 3-го захода, был ошибочным диагнозом, основанным исключительно на абсолютном объёме восстановления `CmaFree` после первой загрузки HEF. При A/B-сравнении официальной vanilla-версии 5.4.0 и версии с исправлением `FOLL_LONGTERM` успешно прошли: последовательная загрузка с низкого `CmaFree`, освобождение и повторная загрузка в одном процессе, генерация 20 раз, а также полный повтор всех испытаний начиная с состояния с ещё более низким `CmaFree`. Во время генерации не наблюдалось монотонного роста или снижения RSS и `CmaFree`, сбоев выделения CMA — ноль. Первоначальное снижение `CmaFree` соответствовало росту использования страничного кэша под multi-GB HEF, при этом `MemAvailable` удерживался на уровне около 7 ГБ. В условиях данного испытания — Pi 5 + Hailo-10H + HailoRT/driver 5.4.0, одна модель, одно устройство, кратковременные повторы — утечка CMA, имеющая практическое значение, не воспроизводится, и исправление `FOLL_LONGTERM` также не даёт измеримого улучшения. Длительная непрерывная эксплуатация, одновременное использование нескольких моделей, Hailo-8, а также работа под IOMMU не тестировались, и данное заключение не распространяется на эти условия.**

## 2. Различия исходного кода v5.3.0 → v5.4.0 (`hailo-ai/hailort-drivers`)

Через GitHub API выполнен diff всех файлов между двумя тегами. Поскольку коммит один и является squash-коммитом, из commit message ничего извлечь нельзя — проверка выполнена по фактическому diff файлов. В **самой логике** выделения и освобождения CMA (пара `dma_alloc_coherent`/`dma_free_coherent`) изменений нет, ниже перечислены в основном рефакторинг и защитные исправления:

| Файл | Содержание изменения |
|---|---|
| `linux/utils/compact.h` → `compat.h` | Переименование файла слоя совместимости с ядром |
| `linux/vdma/memory.c` | В `hailo_desc_list_release()` добавлена проверка на NULL, указатель обнуляется после освобождения (защитное исправление **от двойного освобождения**) |
| `linux/vdma/vdma.h` | Из `hailo_descriptors_list_buffer` удалено избыточное поле `kernel_address` (объединено в `desc_list.descs`) |
| `common/vdma_common.c` | Определение завершения DMA-передачи переписано с прямого вычисления через `hw_num_proc` на сравнение `num_proc`/`num_avail` (возможное исправление бага в отслеживании завершения передачи) |
| `linux/vdma/monitor.c` | `del_timer_sync` → `timer_delete_sync` (следование новому имени API ядра) |
| `common/pcie_common.c` | Из протокола управления FW удалено поле md5, проверка повреждения журнала SCU усилена с проверки только первых 4 байт до проверки всех первых 5 слов |

Также изменена формулировка текста ошибок (длинное пояснение сокращено до `out of CMA memory.`), однако поток управления выделением/освобождением тот же. **Только по этому diff нельзя увидеть изменение, соответствующее тогдашней гипотезе (не освобождение CMA при перезагрузке модели)**.

## 3. Работы по замене на реальном устройстве и возникшие затруднения (2026-08-16, 1-й заход)

На Raspberry Pi 5 + Hailo-10H, с работающим `hailo1x_pci 5.3.0` (под управлением dkms), предпринята попытка ручной сборки для замены на v5.4.0.

### 3.1 `make install` не зависит от `all`

Цель `install` в `linux/pcie/Makefile` содержит только `modules_install` и завершается без предупреждения даже при отсутствии собранного артефакта (`.ko`) (точнее, выводится предупреждение об отсутствии `System.map`, но по нему невозможно понять, что причина — несобранная сборка).

```makefile
install:
	$(Q)$(MAKE) -C $(KERNEL_DIR) M=$(PWD) INSTALL_MOD_DIR=kernel/drivers/misc modules_install
	$(Q)$(DEPMOD) -a

all: $(TARGET_DIR) print-versions
	$(Q)$(MAKE)  -C $(KERNEL_DIR) M=$(PWD) $(GDB_FLAG) $(USER_FLAGS) modules
	$(Q)cp $(DRIVER_NAME_NO_EXT)* $(TARGET_DIR)
```

**Обязательно выполнять в порядке `make all && sudo make install`.**

### 3.2 В заголовках ядра Raspberry Pi отсутствует `System.map`

При выполнении `modules_install` выводится следующее предупреждение, и `depmod` молча пропускается:

```
Warning: modules_install: missing 'System.map' file. Skipping depmod.
```

Причина — отсутствие `/usr/src/linux-headers-<kernelver>/System.map`. Файл `/boot/System.map-<kernelver>` существует, поэтому проблема решается копированием:

```bash
sudo cp /boot/System.map-$(uname -r) /usr/src/linux-headers-$(uname -r)/System.map
sudo depmod -a
```

Если этого не сделать, `modprobe` не сможет разрешить новоустановленный `.ko`, и возникнет `FATAL: Module hailo1x_pci not found` (хотя сам файл `.ko` присутствует в `/lib/modules/<kernelver>/kernel/drivers/misc/`).

### 3.3 Правила udev не применяются немедленно без reload/trigger

`/lib/udev/rules.d/51-hailo-pcie-udev.rules`:

```
SUBSYSTEM=="hailo1x", MODE="0666"
```

Сразу после замены модуля `/dev/h1x-0` становится `crw-------` (доступен только root). Решается следующим образом:

```bash
sudo udevadm control --reload-rules
sudo udevadm trigger --subsystem-match=hailo1x
```

### 3.4 Несовпадение версий driver и library критично

При выполнении `hailortcli` в состоянии, когда обновлён только драйвер ядра до 5.4.0:

```
dmesg: Mismatch Driver version pcie driver 5:4:0 pci_ep driver 5:3:0
dmesg: hailo_soc_get_driver_info has failed with err -22

hailortcli: [HailoRT] [error] CHECK failed - Driver version (5.4.0) is different from library version (5.3.0)
hailortcli: [HailoRT] [error] Driver version mismatch, status HAILO_INVALID_DRIVER_VERSION(76)
```

Библиотека HailoRT требует **полного совпадения** с драйвером ядра, и при опережающем обновлении только одной стороны все вызовы API немедленно отклоняются. Автономная vanilla-проверка одного лишь драйвера невозможна — необходимо одновременно обновить и пользовательский пакет `hailort` (SDK).

- `apt-cache policy hailort` → кандидат 5.3.0 (на текущий момент 5.4.0 в официальном apt не распространяется)
- `gh api repos/hailo-ai/hailort/releases` → тег `v5.4.0` существует, но `assets` пуст (готового deb нет, только исходный код)

То есть **проверка 5.4.0 на реальном устройстве невозможна без установки HailoRT либо через deb, либо путём полной сборки из исходников**. Полная сборка означает крупную сборку C++ CMake + Python-биндингов, с риском затянуть зависимые пакеты вроде `hailo-tappas`, `python3-hailort`, поэтому в 1-м заходе было решено пока отложить это и дождаться официального распространения deb.

## 4. Протокол самостоятельной сборки (2026-08-17, 2-й заход)

Не дожидаясь распространения apt/официального deb, выполнена самостоятельная сборка из исходников GitHub (driver: GPL-2.0, сам `hailort`: MIT) и установка в систему; шаги и возникшие затруднения.

### 4.1 Окружение сборки

- Установлен `checkinstall` (`sudo apt-get install -y checkinstall`). Однако шаг сжатия `xz` для модуля ядра конфликтовал с `installwatch` (механизмом отслеживания файлов checkinstall на базе LD_PRELOAD), и при выполнении `make install` через checkinstall каждый раз возникал сбой `xz: ... そのようなファイルやディレクトリはありません` (файл или каталог не найден). **Для упаковки модуля ядра не использовать checkinstall — использовать dkms (для самого драйвера) либо обычный `make install` (для пользовательской библиотеки)**
- Перед сборкой освобождена память: временно остановлены дублирующиеся процессы `headroom mcp serve` и `rust-analyzer` (освобождено в сумме около 1 ГБ). Памяти на Pi 7.9 Gi, во время сборки удавалось удерживать available на уровне около 3.8 Gi

### 4.2 Сборка `hailort` (пользовательская библиотека)

```bash
git clone --branch v5.4.0 --depth 1 https://github.com/hailo-ai/hailort.git
cd hailort/build   # создать каталог заранее
cmake .. -DCMAKE_BUILD_TYPE=Release   # внешние зависимости (protobuf/spdlog/eigen и др.) автоматически подтягиваются через FetchContent, около 4 минут
cmake --build . -j2   # ограничение -j2 (во избежание нехватки памяти), около 15 минут
sudo make install     # размещается в /usr/local/{include,lib,bin}. Совместимо с версией apt (5.3.0, в /usr)
```

Все опции `option()` по умолчанию отключают тяжеловесные компоненты (GStreamer, тесты, сервер, интеграцию с Ollama и т. п.), поэтому собираются только сравнительно лёгкие `libhailort.so`, `hailortcli`, `libhailopp`.

**Примечание**: результат `make install` размещается в `/usr/local`, версию apt (`/usr`, 5.3.0) он не перезаписывает. При проверке работы необходимо явно указывать путь, например `LD_LIBRARY_PATH=/usr/local/lib /usr/local/bin/hailortcli ...`.

### 4.3 Замена driver (модуля ядра) и обновление firmware

Сам driver собран и установлен через dkms (тем же способом, что описан в процедуре восстановления в Приложении A, с заменой на `-v 5.4.0`), перезагружен через `rmmod`/`modprobe`. На этом этапе `hailortcli` выдавал `HAILO_DRIVER_OPERATION_FAILED(36)`, в dmesg — `Mismatch Driver version pcie driver 5:4:0 pci_ep driver 5:3:0`, и выяснилось, что **прошивку на самом устройстве (сторона SoC, pci_ep) также необходимо отдельно обновить до 5.4.0**.

```bash
# Загрузка firmware из официального S3 (с помощью скрипта, входящего в репозиторий driver)
bash hailort-drivers/download_firmware_hailo10h.sh
# Резервное копирование текущей firmware перед заменой на новую
sudo cp -r /lib/firmware/hailo/hailo10h /lib/firmware/hailo/hailo10h.backup-5.3.0
sudo cp <распакованный путь>/hailo10h_fw_5.4.0/* /lib/firmware/hailo/hailo10h/
sudo chown -R root:root /lib/firmware/hailo/hailo10h/
```

Была предпринята попытка перезагрузки модуля (`rmmod`/`modprobe`, включая указание `support_soft_reset=1`), однако dmesg неизменно возвращал `SOC Firmware batch was already loaded`. При проверке исходного кода драйвера выяснилось, что в `load_soc_firmware()` (путь загрузки прошивки SoC для Hailo-10H) обработка программного сброса через `support_soft_reset` не реализована (она реализована только в `load_nnc_firmware()` для Hailo-8), и пока `hailo_pcie_is_firmware_loaded()` возвращает true, шаг безусловно пропускается. То есть **состояние прошивки на стороне SoC невозможно изменить перезагрузкой модуля, необходим полный перезапуск питания устройства**.

После перезагрузки dmesg зафиксировал запись пакета firmware (в порядке `customer_certificate.bin`, `scu_fw.bin`, `u-boot-*.dtb.signed`, `u-boot-spl.bin`, `fitImage`, `image-fs`, 4064 мс) → `SOC Firmware Batch loaded successfully`, а `hailortcli fw-control identify` штатно ответил `Firmware Version: 5.4.0 (release,app)`.

### 4.4 Упрощённая проверка поведения CMA и её ограничения

С помощью `hailortcli run2` (`resnet_v1_18.hef`, небольшая модель из комплекта пакета `hailo_tutorials`) выполнены однократный load/run/exit, а также наблюдение динамики `CmaFree` (`/proc/meminfo`) при 8 последовательных запусках:

| Запуск | CmaFree (kB) |
|---|---|
| baseline (сразу после перезагрузки) | 170464 |
| итерация 1 | 134864 |
| итерация 2 | 134144 |
| итерации 3–8 | 133744 (без изменений, плато) |

Плато достигнуто за несколько запусков, до 8-го запуска дополнительной утечки не наблюдалось. Однако это простой load/run/exit через CLI (запуск в отдельном процессе каждый раз) — путь, отличающийся от обеих известных утечек, о которых сообщает `docs/development/development_docs/HAILO_FORUM_FOLLOWUP_CMA_INFERENCE_LEAK.md`: (a) не освобождение при `VDevice.release()`/перезагрузке модели **в одном и том же процессе**, (b) непрерывная утечка во время выполнения `generate_stream()` (LLM-инференс). Этот результат не является доказательством того, что проблема «решена».

Основной repro (`tools/diag_hailo_cma_reclaim.py` и скрипт, описанный в forum-followup документе) построен на загрузке GenAI LLM через биндинг Python `hailo_platform` (pyhailort), поэтому в текущем окружении 5.4.0 запустить его напрямую не удалось:

```
$ hailo_platform внутри .venv статически связан с libhailort.so.5.3.0 (проверено через ldd)
$ Ожидается, что при конструировании VDevice() возникнет тот же HAILO_INVALID_DRIVER_VERSION из-за несовпадения версий driver(5.4.0)/library(5.3.0)
```

На этот момент пересборка pyhailort (Python-биндинга) из исходников 5.4.0 с заменой в `.venv` ещё не была начата — она выполнена в 3-м заходе (§5).

## 5. Пересборка pyhailort и повторный запуск repro (2026-08-17, 3-й заход)

Настоящий раздел фиксирует предварительный диагноз на момент 3-го захода. Метод диагностики и заключение исправлены в ходе финального A/B-теста 4-го захода (§8).

### 5.1 Сборка pyhailort (Python-биндинга)

`hailort/libhailort/bindings/python/platform/` в основном репозитории `hailort` — исходник pip-пакета pyhailort (на базе `pyproject.toml`, scikit-build-core + pybind11). Собран с явной привязкой к libhailort 5.4.0, размещённой в `/usr/local` согласно §4.2:

```bash
cd hailort/libhailort/bindings/python/platform
CMAKE_ARGS="-DLIBHAILORT_PATH=/usr/local/lib/libhailort.so.5.4.0 -DHAILORT_INCLUDE_DIR=/usr/local/include" \
  <venv>/bin/python -m pip install .
```

Внутри build isolation `scikit-build-core`/`pybind11` автоматически загружены с PyPI, `hailort` в `.venv` заменён с wheel 5.3.0 на 5.4.0. Через `ldd` подтверждено, что `_pyhailort*.so` слинкован с `/usr/local/lib/libhailort.so.5.4.0`, конструирование/освобождение `VDevice()` также штатно отработало отдельно.

### 5.2 Повторный запуск существующего repro (`tools/diag_hailo_cma_reclaim.py`)

С тем же скриптом repro, тем же критерием диагностики и тем же HEF (`~/hailo_models/Qwen3-1.7B-Instruct.hef`), что и в 2026-05, в том же окружении, но с заменённым на 5.4.0 `hailo_platform` в `.venv`, выполнено повторное измерение:

```bash
uv run python tools/diag_hailo_cma_reclaim.py --signal terminate
```

Результат (`logs/hailo_cma_reclaim_poc.json`):

| Событие | CmaFree (MB) |
|---|---|
| baseline_before_spawn | 159 |
| after_vdevice_created / after_llm_loaded | 22 (израсходовано 137 MB) |
| сразу после child kill (`terminate`) | 23 |
| post_wait +5s | 26 |
| post_wait +10s | 28 |
| post_wait +15s | 29 |
| post_wait +20s…+30s | **0** (дальнейшее снижение с 29 MB примерно на 28.5 MB, впоследствии `CmaFree` в течение нескольких минут держался около 512 kB) |

Это повторное снижение с 29 MB до около 512 kB не удалось подтвердить как конкуренцию с другими процессами в тот же момент, однако одним этим измерением причину установить нельзя, и оно остаётся неразрешённым наблюдением. Использование страничного кэша после первой загрузки (§8.4) само по себе не объясняет этот промежуточный ход событий, а повторного испытания с одновременным сбором RSS, `MemAvailable` и данных о сбоях выделения в этом запуске не проводилось, поэтому оно не используется как основание для итогового заключения §8.

При этом диапазон около 512 kB совпадает с диапазоном 464→1 648 kB, наблюдавшимся при испытании `FOLL_LONGTERM` в §8.3, и из этого состояния успешно выполнены 20-кратная генерация, освобождение и повторная загрузка. Путь достижения низкого значения остаётся невыясненным, но на реальном устройстве подтверждено, что **само по себе `CmaFree` в этом диапазоне не означает немедленно опасное состояние или невозможность загрузки**.

Исходный вывод старого диагностического инструмента (предварительный диагноз на момент 3-го захода; итоговое заключение исправлено в §8):

```
VERDICT: FAIL — only -22 MB recovered after kill+wait. spec hypothesis invalid → pivot to auto-reboot alternatives
```

В этом испытании установлено лишь то, что `CmaFree` после первой загрузки HEF не восстановился согласно старому критерию. Ни утрата доступной памяти после завершения процесса, ни неустранённость утечки в v5.4.0 доказаны не были. В 3-м заходе это было предварительно истолковано как не освобождение, но данная интерпретация и метод диагностики исправлены в §8.

## 6. Крах ядра во время 3-го захода и восстановление отладочного кода CMA (2026-08-17)

### 6.1 Событие и предполагаемая причина

Для исследования пути освобождения CMA в `linux/vdma/memory.c` локального DKMS-исходника были добавлены include `linux/mm.h` и измерительный код, вызывающий `virt_to_page()` / `page_count()` непосредственно перед `dma_free_coherent()`. При загрузке модуля с этим изменением при использовании Hailo происходило зависание, устройство переставало загружаться, поэтому автозагрузка сейчас остановлена через `module_blacklist=hailo1x_pci,hailo_pci` в `/boot/firmware/cmdline.txt`.

Прямое преобразование CPU-виртуального адреса, возвращаемого `dma_alloc_coherent()`, в страницу через `virt_to_page()` не является частью контракта DMA API. Формат отображения возвращаемого адреса остаётся на усмотрение аллокатора, поэтому получаемый таким образом `page_count()` не является корректным способом наблюдения за количеством ссылок CMA и может привести к некорректному обращению к страницам. Измерительный код выполнялся на обоих путях освобождения — и для descriptor list, и для continuous buffer.

Время добавления кода — 10:15:36, начало соответствующей сборки DKMS — 10:15:39, поэтому можно заключить, что зависший модуль содержал этот код. Стек-трейс непосредственно перед крахом получить не удалось, поэтому строгого установления причины нет, но это единственное локальное изменение исполняемого кода, отсутствующее в vanilla v5.4.0, и оно рассматривается как наиболее вероятный кандидат в причины.

### 6.2 Восстановленное состояние

Удалены следующие 7 строк (include `linux/mm.h`, два места с логированием `virt_to_page()` / `page_count()`), DKMS пересобран, выполнен вплоть до `depmod`.

- Ядро: `6.18.39+rpt-rpi-2712`
- Пересобранный модуль: `/lib/modules/6.18.39+rpt-rpi-2712/updates/dkms/hailo1x_pci.ko.xz`
- В `modules.dep` указанный модуль зарегистрирован
- blacklist сохраняется, пересобранный модуль пока не загружался

В дальнейшем планируется обеспечить путь восстановления (например, через серийную консоль), после чего снять blacklist и подтвердить первую загрузку через перезагрузку. В самом исследовании проблемы не освобождения CMA измерительный код, преобразующий возвращаемый адрес DMA API во внутреннюю страницу, повторно вводиться не будет — объектами наблюдения станут журнал буферов, размеры выделений и число вызовов `dma_free_coherent()`, которые ведёт сам драйвер.

**Дополнение (2026-08-17, позднее)**: подготовлена резервная копия `cmdline.txt` (`cmdline.txt.bak-blacklisted`), после чего blacklist снят и выполнена перезагрузка — подтверждён штатный запуск (также настроена серийная консоль `console=serial0,115200`, путь восстановления обеспечен). Далее исследование продолжено с безопасным инструментированием §7 (без проверки сырых страниц, только вывод существующих счётчиков и размеров в журнал).

## 7. Формирование и исключение гипотез о причине — проверка и опровержение `FOLL_LONGTERM` (2026-08-17)

Настоящий раздел фиксирует формирование гипотез о причине по итогам 3-го захода и кандидатов, исключённых экспериментально. Роль данного раздела — сужение круга кандидатов; итоговое заключение о наличии/отсутствии утечки CMA зависит от финального A/B-теста 4-го захода (§8).

С учётом краха в §6 исследование продолжено с безопасным инструментированием, избегающим прямого доступа к внутренним структурам страниц через `virt_to_page()` и т. п. (только вывод в журнал через `dev_err()`, без проверки/преобразования сырых указателей).

### 7.1 Содержание инструментирования

В следующие места `linux/vdma/memory.c` / `linux/vdma/ioctl.c` / `linux/vdma/vdma.c` добавлено логирование значений уже существующих атомарных счётчиков (`controller->desc_cma_in_use` / `controller->cma_in_use`) и размеров выделений (без какого-либо обращения к внутренним структурам страниц):

- `hailo_desc_list_create`/`hailo_desc_list_release` (alloc/free descriptor list)
- `hailo_vdma_continuous_buffer_alloc`/`hailo_vdma_continuous_buffer_free` (alloc/free continuous buffer)
- `hailo_desc_list_release_ioctl`/`hailo_vdma_continuous_buffer_free_ioctl` (пути явного освобождения через ioctl)
- `hailo_vdma_buffer_map`/`hailo_vdma_buffer_destroy` (путь DMA-маппинга/анмаппинга пользовательского буфера; также выводятся `buffer_type`/`is_mmio`/`is_dmabuf`)
- `hailo_vdma_file_context_finalize` (единая очистка при fops_release, счётчики выводятся на ENTER/EXIT)

### 7.2 Результаты наблюдения

Сразу после перезагрузки (`CmaFree` ≈ 451 MB) выполнен `tools/diag_hailo_cma_reclaim.py --signal terminate`, все журналы собраны и агрегированы через `sudo dmesg | grep CMA_DBG`.

- **`CmaFree` в `/proc/meminfo`**: 451 MB → 195 MB (**израсходовано 256 MB**) → через 30 секунд после kill+wait по-прежнему 204 MB (**на 247 MB ниже baseline**)
- **`desc_cma_in_use` самого драйвера (descriptor list, через `dma_alloc_coherent`)**: максимум порядка 2–4 MB. На выходе из `file_context_finalize` достоверно возвращается к 0
- **`cma_in_use` (continuous buffer, через `dma_alloc_coherent`)**: в течение всей сессии неизменно 0 (continuous buffer не использовался ни разу)
- **DMA-маппинг пользовательского буфера (`hailo_vdma_buffer_map`, `buffer_type=0`=`HAILO_DMA_USER_PTR_BUFFER`, `is_mmio=0`, `is_dmabuf=0`)**: вызван 621 раз, из них **342 раза с размером 8 MB (`0x800000`)** (в сумме вызовы маппинга на 2.7 GB; по всей видимости, один и тот же хостовый staging-буфер многократно переиспользуется в конвейерной обработке). `hailo_vdma_buffer_destroy` вызван 628 раз, что практически соответствует `buffer_map` 1 к 1 — **как учётная книга собственного маппинга драйвера противоречий нет** (`dma_unmap_sg` вызывается корректно)
- **SWIOTLB (`/sys/kernel/debug/swiotlb/`)**: `io_tlb_used_hiwater=0`. Bounce-буфер не использовался ни разу
- Устройство Hailo не находится под IOMMU (`/sys/bus/pci/devices/0001:01:00.0/iommu_group` отсутствует)

На этом этапе в качестве кандидата на причину снижения CMA был выбран не собственный аллокатор драйвера через `dma_alloc_coherent()` (desc list, continuous buffer), а путь, обрабатываемый `hailo_vdma_buffer_map()`, — «маппинг уже выделенной пользователем памяти для DMA» (`HAILO_DMA_USER_PTR_BUFFER`). На этом пути драйвер не выделяет новый CMA, а фиксирует (pin) уже существующие страницы пользователя, чтобы сделать их доступными для DMA.

### 7.3 Гипотеза о причине: в `get_user_pages()` не указан `FOLL_LONGTERM`

При проверке `prepare_sg_table()` (вызывается изнутри `hailo_vdma_buffer_map()`) в `linux/vdma/memory.c`:

```c
pinned_pages = compat_get_user_pages(user_address, npages, FOLL_WRITE | FOLL_FORCE, pages);
```

`compat_get_user_pages` (поскольку используемое ядро 6.18.39 удовлетворяет `LINUX_VERSION_CODE >= KERNEL_VERSION(6, 5, 0)`) является просто алиасом `get_user_pages()`, и **флаг `FOLL_LONGTERM` не указан**. На стороне освобождения (`clear_sg_table()`) также вызывается соответствующий `put_page()` — то есть используется не новое семейство API `pin_user_pages()`/`unpin_user_pages()`, а прежние `get_user_pages()`/`put_page()`.

Согласно задокументированной практике ядра Linux (`Documentation/core-api/pin_user_pages.rst`), код, который **удерживает ссылку на страницу длительное время**, как в случае DMA-передачи, должен использовать `pin_user_pages()` с флагом `FOLL_LONGTERM`. Если `FOLL_LONGTERM` не указан, а пользовательская страница, случайно оказавшаяся в области CMA, фиксируется через `get_user_pages()`, свойство CMA «можно переместить при необходимости под другую цель» (migratable) на длительное время отключается для этой страницы. Обычно аллокатор CMA перед долгосрочной фиксацией мигрирует такую страницу за пределы области CMA, но на пути без `FOLL_LONGTERM` эта миграция не происходит, поэтому **пока страница зафиксирована, она фактически теряется из области CMA на этот объём, и даже после освобождения (`put_page()`) она не сразу распознаётся как свободное место CMA** (требуется дополнительная миграция/компактация).

Эта гипотеза согласовывалась с однократным измерением 3-го захода (§7.2):
- Собственные счётчики CMA драйвера не имеют отношения к делу (`get_user_pages` не проходит через `dma_alloc_coherent`)
- Число вызовов map/destroy сбалансировано корректно (сам `put_page()` вызывается верно; проблема в медленном/неполном «возврате» в CMA после освобождения)
- При загрузке крупной LLM вроде Qwen3-1.7B-Instruct выделяется и DMA-маппируется большое количество 8 MB буферов в хостовой памяти, и проблема проявляется, когда часть из них включает страницы из области CMA
- Согласуется и с медленным, частичным восстановлением `CmaFree` после kill (порядка +15–30 MB за 30 секунд, далее плавный рост в течение нескольких минут) (сам `put_page()` достоверно вызывается при завершении процесса, но для возврата в качестве свободного места CMA, по-видимому, требуется дополнительная обработка)

### 7.4 Реализация кандидата на исправление и проверка на реальном устройстве → опровержение (2026-08-17, продолжение)

`prepare_sg_table()` фактически заменён с `get_user_pages(FOLL_WRITE | FOLL_FORCE)` + `put_page()` на `pin_user_pages(FOLL_WRITE | FOLL_FORCE | FOLL_LONGTERM)` + `unpin_user_page()`, добавлен include `<linux/mm.h>`, выполнены сборка, перерегистрация dkms и загрузка на реальном устройстве (подтверждено через `modprobe --dump-modversions`, что символы `pin_user_pages`/`unpin_user_page` штатно разрешаются).

Результат того же repro, выполненного из состояния высокого `CmaFree` (453 MB) сразу после перезагрузки:

| | до исправления (n=несколько прогонов) | после исправления (n=1) |
|---|---|---|
| baseline | 436–451 MB | 453 MB |
| after_llm_loaded | 173–195 MB (израсходовано 256–263 MB) | 180 MB (израсходовано 273 MB) |
| after_post_wait | 188–204 MB (восстановлено 9–15 MB) | 190 MB (**восстановлено 10 MB**) |
| `VERDICT` по старому критерию | `FAIL` | **`FAIL` (без изменений)** |

> Эта таблица асимметрична по числу прогонов и способу агрегирования и не является строгим A/B-сравнением. A/B-оценка выполнена на данных §8, полученных при повторах в одинаковых условиях.

При проверке `CMA_DBG buffer_map` через `dmesg` установлено, что и после исправления те же буферы размером 0x800000 (8 MB) без проблем маппируются через `pin_user_pages` (сбоев pin или предупреждений ядра не возникло) — путь кода выполнялся как задумано. Принудительная компактация через `echo 1 > /proc/sys/vm/compact_memory` также не дала эффекта. `MemAvailable` оставался в норме на уровне 7.1 GB, и, как и до исправления, дефицита общей памяти системы не было — не восстанавливался именно отдельный учёт `CmaFree`.

**Заключение: гипотеза об отсутствии `FOLL_LONGTERM` опровергнута экспериментально.** Замена `get_user_pages()`→`pin_user_pages()`+`FOLL_LONGTERM` является правомерным улучшением, соответствующим задокументированной практике ядра Linux, однако не была прямой причиной симптома не освобождения CMA, наблюдавшегося в этой сессии. Сама гипотеза теоретически обоснована (взаимодействие механизма миграции CMA и долгосрочной фиксации — реально существующий известный класс проблем), и как замечание по качеству кода она остаётся в силе, но **не объясняет в одиночку полученный в этот раз результат измерения**.

### 7.5 Исключённые кандидаты на причину (итоговое заключение — в §8)

Ниже перечислены кандидаты на причину, чётко **исключённые** экспериментально. Этот список — результат проверки гипотез, но сам по себе не является заключением о наличии/отсутствии утечки.

- Собственные выделения драйвера через `dma_alloc_coherent()` (desc list, continuous buffer) — всего несколько MB, корректно возвращаются к 0
- Несоответствие вызовов map/destroy для SG-маппинга — сбалансировано
- Bounce-буфер SWIOTLB — не использовался ни разу (`io_tlb_used_hiwater=0`)
- Отсутствие `FOLL_LONGTERM` в `get_user_pages()` — исправление реализовано и проверено на реальном устройстве, улучшения нет

Факт, остававшийся неразрешённым к концу 3-го захода, — то, что при исправном `MemAvailable` именно `CmaFree` снижался после первой загрузки. На тот момент это интерпретировалось как не освобождение, однако однократное испытание не позволяет отличить «утрату доступной памяти» от «переиспользования перемещаемых страниц CMA под страничный кэш». В 4-м заходе выполнены повторные попытки из состояния низкого `CmaFree`, измерены фактическая возможность загрузки, чистое снижение при повторах, RSS и сбои выделения CMA — диагноз исправлен.

## 8. 4-й заход: повторное A/B-испытание vanilla / `FOLL_LONGTERM` и подтверждение ошибочного диагноза (2026-08-17)

### 8.1 Сравниваемые объекты

- Версия с исправлением `FOLL_LONGTERM`: `pin_user_pages(FOLL_LONGTERM)` / `unpin_user_page()`, при загрузке `srcversion=C84A00ABB326748A1832CE1`
- Официальная vanilla-версия 5.4.0: тег `v5.4.0`, коммит `b6dd17c609504e648eb516ff4a867167edf56f3c`, `get_user_pages()` / `put_page()`, при загрузке `srcversion=A260C39C9F2C06DD4FB072E`
- Ядро: `6.18.39+rpt-rpi-2712`
- HEF: `Qwen3-1.7B-Instruct.hef` (2 880 748 478 байт)

### 8.2 Две последовательные загрузки в независимых процессах

| Драйвер | Попытка | baseline | loaded | после exit | разница относительно baseline | загрузка |
|---|---:|---:|---:|---:|---:|---|
| `FOLL_LONGTERM` | 1 | 338 MB | 34 MB | 25 MB | **-313 MB (снижение)** | успешно |
| `FOLL_LONGTERM` | 2 | 5 MB | 6 MB | 7 MB | **+2 MB (рост)** | успешно |
| vanilla | 1 | 376 MB | 99 MB | 112 MB | **-264 MB (снижение)** | успешно |
| vanilla | 2 | 125 MB | 118 MB | 124 MB | **-1 MB (снижение)** | успешно |

Для обоих драйверов `CmaFree` заметно снижался только при первой попытке, а вторая загрузка из этого уже низкого значения проходила успешно, и чистое снижение оказывалось практически нулевым. Прежняя диагностика оценивала только «сколько MB из израсходованного при загрузке вернулось», поэтому нормальные случаи вроде второй попытки, где `CmaFree` изначально уже низкий, также помечались как `FAIL`.

### 8.3 Генерация, освобождение и повторная загрузка в одном процессе

| Показатель | `FOLL_LONGTERM` | vanilla, 1-й прогон | vanilla, повтор с низким CMA |
|---|---:|---:|---:|
| Завершено генераций | 20/20 | 20/20 | 20/20 |
| 1-я загрузка | успешно | успешно | успешно |
| 2-я загрузка после освобождения | успешно | успешно | успешно |
| `CmaFree` от генерации 1 до 20 | 464→1 648 kB | 115 376→123 728 kB | 82 320→83 296 kB |
| `MemAvailable` от генерации 1 до 20 | 6 706 208→6 788 432 kB | 6 830 352→6 910 560 kB | 6 871 504→6 906 368 kB |
| RSS во время генерации | стабильно 63 888 kB | 63 904–63 920 kB | 63 936–63 952 kB |

Повтор с низким CMA на vanilla начат при `CmaFree=87,424 kB`, сразу после полного освобождения — 79 520 kB, впоследствии вернулся к 87 344 kB (чистая разница 80 kB). Поведения, при котором повторение загрузки, генерации и освобождения приводило бы к потерям, не наблюдается. То, что `nr_foll_pin_*` у vanilla равен 0, объясняется тем, что API `FOLL_PIN` не используется — для сравнения успешности освобождения pin этот показатель непригоден.

### 8.4 Интерпретация первоначального снижения

От момента сразу после перезагрузки vanilla до завершения всех повторных испытаний `Cached` вырос примерно с 1 845 872 kB до около 4 988 224 kB, при этом `MemAvailable` удерживался с 7 071 280 kB на уровне около 6 962 816 kB. Объём прироста согласуется с чтением multi-GB HEF, и первоначальное снижение `CmaFree` можно объяснить не утратой недоступной памяти, а использованием под страничный кэш свободных страниц, включая перемещаемые страницы CMA.

### 8.5 Операционное заключение

1. Нельзя отклонять загрузку модели только по абсолютному значению `CmaFree`. На реальном устройстве загрузка Qwen прошла успешно даже при значении менее 1 MB.
2. Низкий `CmaFree` следует фиксировать как телеметрию, а для решения об отказе использовать фактическую ошибку выделения памяти со стороны HailoRT.
3. Не смешивать наблюдаемое значение `CmaFree`, фактический сбой загрузки и диагностику утечки — обрабатывать как три отдельных состояния:

| Состояние | Условие определения | Действие на стороне продукта | Перезагрузка / расследование |
|---|---|---|---|
| `INCONCLUSIVE` | Только первоначальное снижение, менее 3 повторов, либо условие `FAIL` ниже не выполняется | Записать телеметрию и попытаться выполнить загрузку. Не отклонять только по низкому `CmaFree` | Не перезагружать. Продолжить измерения в тех же условиях |
| `OPERATIONAL_FAIL` | HailoRT фактически вернул ошибку выделения host-памяти | Считать неудачной только этот конкретный запрос на загрузку, остановить ненужную нагрузку Hailo и повторить попытку | При единичном случае не перезагружать. Только если реальный сбой повторяется и не устраняется после освобождения нагрузки — следовать операционной политике. На текущем этапе Phase 0.5 только фиксируется `would_fire`, автоматической перезагрузки нет |
| `FAIL` | При повторении одних и тех же условий из состояния низкого CMA 3 раза: чистое снижение относительно baseline после освобождения превышает 10 MB **в 2 из 3 или более попытках**, суммарное положительное чистое снижение за 3 попытки превышает 20 MB, и при этом наблюдается монотонный рост RSS либо снижение `MemAvailable` более чем на 128 MB | Фиксировать как диагностику утечки отдельно от возможности отдельных загрузок | Возобновить расследование на стороне ядра / HailoRT, собрать прямые доказательства. Сама по себе постановка диагноза не приводит к автоматической перезагрузке |

Этот критерий трёх повторов предназначен для будущей диагностики и ретроспективно не применяется к §8.2 этого раздела, где для каждого драйвера было выполнено только по 2 попытки в независимых процессах. Заключение 4-го захода объединяет A/B из §8.2 с 20-кратной генерацией/освобождением/повторной загрузкой в одном процессе и повтором с низким CMA из §8.3.
4. Замена на `FOLL_LONGTERM` разумна как общепринятая практика Linux DMA API, но эффекта для данного случая не даёт — реальное устройство возвращено к официальной vanilla-версии 5.4.0.
5. Решение об автоматической перезагрузке не должно срабатывать только по низкому `CmaFree` — обязательным условием остаётся наблюдение фактического сбоя загрузки.

## 9. Дальнейшие действия (на 2026-08-17)

1. Рассмотрение исправления `FOLL_LONGTERM` и его опровержение на реальном устройстве завершены. Диффы для воспроизведения и способ восстановления сохранены в Приложении B, в продуктовый драйвер не применяются.
2. **На стороне продукта уже принята мера**: `core/hailo_device_core/device_manager_genai.py::acquire_genai` начиная с v4.620.8 доработан так, что при `CmaFree` ниже расчётной необходимой величины фиксируется `acquire_low_cma_observed`, но фактическая загрузка продолжается. В tracker отказов записывается только реальная ошибка host-памяти, возвращённая factory HailoRT; продолжение загрузки при низком значении закреплено в `tests/test_hailo_cma_false_positive.py`.
3. Утверждение из старого черновика форума о том, что «последующий `LLM(...)` был отклонён HailoRT из-за insufficient host CMA», повторно проверено по журналам и старой реализации. В сессии с PID 3237, на которую опирается цитата, записи об acquire после release не было, и все отказы по низкому CMA, прослеживаемые в журнале за тот же день, оказались собственным событием `acquire_rejected_low_cma`, срабатывающим до вызова HailoRT. В другой сессии, где сбой дошёл до factory, был статус 8 (`HAILO_INTERNAL_FAILURE`), а не статус 3 (ошибка host-памяти). Соответственно, подтверждающих старую запись доказательств OOM со стороны HailoRT нет; в `docs/development/development_docs/HAILO_FORUM_FOLLOWUP_CMA_INFERENCE_LEAK.md` явно указано, что в отчёт попал отказ, вызванный собственной защитой, и это утверждение отозвано.
4. Исправленная публикация объединит цифры и область применения §8, исправление реализованной защиты, опровержение `FOLL_LONGTERM` и предупреждения об инструментировании в единый актуальный черновик; старый англоязычный черновик в копируемом виде сохраняться не будет.
5. Расследование утечки на стороне ядра / HailoRT будет возобновлено только в случае, если фактически повторится сбой загрузки либо накопительная утрата доступной памяти при повторах. В таком случае будут собраны прямые доказательства — `page_owner`, отладочная информация CMA, статус сбоя выделения, RSS, `MemAvailable` и т. п.

## Приложение A. Процедура восстановления до v5.3.0

После однократного выполнения `remove --all` из dkms восстановление невозможно через `apt-get install --reinstall`, если в кэше apt не осталось `.deb` (в данном случае сбой действительно произошёл: `ダウンロードできないため、再インストールは不可能` — переустановка невозможна из-за невозможности загрузки). Поскольку dpkg по-прежнему считает пакет `hailort-pcie-driver` установленным (`ii`), если каталог развёртывания исходников пакета `/usr/src/hailort-pcie-driver/` не удалён, дерево dkms можно восстановить вручную из него:

```bash
sudo rmmod hailo1x_pci

sudo rm -rf /usr/src/hailo1x_pci-5.3.0
sudo cp -r /usr/src/hailort-pcie-driver /usr/src/hailo1x_pci-5.3.0
sudo sed 's/@PCIE_DRIVER_VERSION@/5.3.0/' \
  /usr/src/hailo1x_pci-5.3.0/linux/pcie/dkms.conf.in \
  | sudo tee /usr/src/hailo1x_pci-5.3.0/linux/pcie/dkms.conf > /dev/null

# dkms.conf нужно разместить непосредственно в корне дерева (в linux/pcie/ приведёт к ошибке)
sudo cp /usr/src/hailo1x_pci-5.3.0/linux/pcie/dkms.conf /usr/src/hailo1x_pci-5.3.0/dkms.conf

sudo dkms add -m hailo1x_pci -v 5.3.0
sudo dkms build -m hailo1x_pci -v 5.3.0 -k $(uname -r)
sudo dkms install -m hailo1x_pci -v 5.3.0 -k $(uname -r) --force
sudo depmod -a
sudo modprobe hailo1x_pci
sudo udevadm trigger --subsystem-match=hailo1x
```

Проверка восстановления:

```bash
cat /sys/module/hailo1x_pci/version   # → 5.3.0
hailortcli fw-control identify        # → штатный ответ означает, что восстановление завершено
```

### B.2 Проверка перед применением

Ниже выполняется только в случае, если `/usr/src/hailo1x_pci-5.4.0` на Raspberry Pi указывает на упомянутый выше официальный коммит и в трёх целевых файлах нет локальных изменений. Если коммит, контрольная сумма патча или контрольная сумма vanilla-версии `memory.c` не совпадают — остановиться; принудительно применять патч нельзя.

```bash
set -euo pipefail

REPO=/home/pi/GitHub/yu_ai_manager
SRC=/usr/src/hailo1x_pci-5.4.0
PATCH="$REPO/docs/development/patches/hailo1x_pci-5.4.0-foll-longterm-cma-debug-experiment.patch"
EXPECTED_HEAD=b6dd17c609504e648eb516ff4a867167edf56f3c
EXPECTED_PATCH_SHA=7b5c4027f37432dbbbe39e4bdec2f0f5e8dd87e133473b5a44c44b1e86c5503f
EXPECTED_MEMORY_SHA=85d564acaa70cdb41eb18bad35ad958d3b2af168ae03c17466976cbe64b1e58c

test "$(sudo git -c safe.directory="$SRC" -C "$SRC" rev-parse HEAD)" = "$EXPECTED_HEAD"
printf '%s  %s\n' "$EXPECTED_PATCH_SHA" "$PATCH" | sha256sum -c -
printf '%s  %s\n' "$EXPECTED_MEMORY_SHA" "$SRC/linux/vdma/memory.c" | sha256sum -c -
sudo git -c safe.directory="$SRC" -C "$SRC" diff --exit-code -- \
  linux/vdma/ioctl.c linux/vdma/memory.c linux/vdma/vdma.c
sudo git -c safe.directory="$SRC" -C "$SRC" apply --check "$PATCH"
```

### B.3 Применение экспериментального патча

Только если все проверки прошли успешно, патч применяется и модуль DKMS устанавливается для следующей загрузки. Загруженный модуль вручную не заменяется через `rmmod` / `modprobe`; переключение происходит через обычную перезагрузку после сборки.

```bash
set -euo pipefail

SRC=/usr/src/hailo1x_pci-5.4.0
PATCH=/home/pi/GitHub/yu_ai_manager/docs/development/patches/hailo1x_pci-5.4.0-foll-longterm-cma-debug-experiment.patch
KERNEL_VERSION="$(uname -r)"

sudo git -c safe.directory="$SRC" -C "$SRC" apply "$PATCH"
sudo dkms build -m hailo1x_pci -v 5.4.0 -k "$KERNEL_VERSION" --force
sudo dkms install -m hailo1x_pci -v 5.4.0 -k "$KERNEL_VERSION" --force
sudo depmod -a "$KERNEL_VERSION"

modinfo -n hailo1x_pci
modinfo -F srcversion hailo1x_pci
head -n 1 /sys/module/hailo1x_pci/srcversion
```

`modinfo` показывает модуль, установленный для следующей загрузки, а `/sys/module/.../srcversion` — модуль, загруженный в данный момент. То, что на этом этапе значения различаются, — норма. Когда всё готово, выполняется перезагрузка, и после запуска проверяется совпадение обоих значений.

```bash
sudo reboot

# после повторного подключения
modinfo -F srcversion hailo1x_pci
head -n 1 /sys/module/hailo1x_pci/srcversion
```

В том же проверочном окружении ожидаемое значение после применения патча — `C84A00ABB326748A1832CE1`. Если значение отличается, не продолжать испытания на основе догадок — проверить диф исходника, ядро, журнал сборки DKMS.

### B.4 Восстановление до официальной vanilla-версии 5.4.0

Восстановление не полагается на обратное применение патча — три целевых файла явно возвращаются из проверенного коммита. Это исключает состояние, при котором применение осталось бы частичным или сохранился бы только инструментальный код.

```bash
set -euo pipefail

SRC=/usr/src/hailo1x_pci-5.4.0
EXPECTED_HEAD=b6dd17c609504e648eb516ff4a867167edf56f3c
EXPECTED_MEMORY_SHA=85d564acaa70cdb41eb18bad35ad958d3b2af168ae03c17466976cbe64b1e58c
KERNEL_VERSION="$(uname -r)"

test "$(sudo git -c safe.directory="$SRC" -C "$SRC" rev-parse HEAD)" = "$EXPECTED_HEAD"
sudo git -c safe.directory="$SRC" -C "$SRC" restore --source="$EXPECTED_HEAD" -- \
  linux/vdma/ioctl.c linux/vdma/memory.c linux/vdma/vdma.c
sudo git -c safe.directory="$SRC" -C "$SRC" diff --exit-code -- \
  linux/vdma/ioctl.c linux/vdma/memory.c linux/vdma/vdma.c
printf '%s  %s\n' "$EXPECTED_MEMORY_SHA" "$SRC/linux/vdma/memory.c" | sha256sum -c -

sudo dkms build -m hailo1x_pci -v 5.4.0 -k "$KERNEL_VERSION" --force
sudo dkms install -m hailo1x_pci -v 5.4.0 -k "$KERNEL_VERSION" --force
sudo depmod -a "$KERNEL_VERSION"

modinfo -F srcversion hailo1x_pci
head -n 1 /sys/module/hailo1x_pci/srcversion
```

В том же проверочном окружении ожидаемое значение установленного vanilla-модуля — `A260C39C9F2C06DD4FB072E`. Убедившись, что текущее загруженное значение отличается, выполняется перезагрузка, и после повторного подключения проверяется, что оба значения стали `A260C39C9F2C06DD4FB072E`.
