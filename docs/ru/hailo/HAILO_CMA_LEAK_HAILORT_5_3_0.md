# Утечка CMA в HailoRT 5.3.0 — Подтверждённый диагноз и операционные ограничения

> **Примечание об исправлении**: Настоящий документ является записью старой диагностики утечки CMA. Прежний вывод — что CMA не возвращается даже после `release()`, что во время инференса продолжается утечка со скоростью примерно 14 МБ/мин, и что единственный надёжный способ восстановления — перезагрузка Pi — отозван. Окончательное заключение по итогам повторного тестирования на HailoRT/driver 5.4.0 приведено с исправлением в §8 документа [HAILO_5_4_0_DRIVER_VANILLA_TRIAL.md](HAILO_5_4_0_DRIVER_VANILLA_TRIAL.md). Не используйте старый вывод настоящего документа как актуальное практическое заключение.

**Создано**: 2026-05-17 (обнаружено и задокументировано в v4.214.11)
**Область влияния**: Raspberry Pi 5 + Hailo-10H + `hailort==5.3.0` (путь `hailo_platform.genai`)
**Симптом**: После загрузки LLM CMA почти не возвращается даже после вызова `VDevice.release()` / `LLM.release()`. Кроме того, во время инференса CMA продолжает непрерывно утекать. Нет способа восстановления кроме перезагрузки Pi.
**Статус**: Подтверждено как структурное ограничение на стороне драйвера. Способы обхода изучаются.

---

## 1. Основание для подтверждённого диагноза

С помощью регистратора событий CMA, введённого в `v4.214.10` (`logs/hailo_cma.log`, `core/hailo_device_core/device_helpers.py::log_hailo_cma_event`), 2026-05-17 была измерена следующая последовательность.

### 1-1. Журнал наблюдений (raw)

`logs/hailo_cma.log`:

```text
2026-05-17T14:05:13+0900 event=vdevice_create_pre  cma_free_mb=392 pid=3237
2026-05-17T14:05:14+0900 event=vdevice_create_post cma_free_mb=393 pid=3237
2026-05-17T14:05:14+0900 event=acquire_pre  cma_free_mb=393 pid=3237 owner=llm hef=Qwen3-1.7B-Instruct.hef
2026-05-17T14:06:25+0900 event=acquire_post cma_free_mb=108 pid=3237 owner=llm hef=Qwen3-1.7B-Instruct.hef
        ↓ 6 минут использования чата (примерно 5–10 сообщений инференса)
2026-05-17T14:12:36+0900 event=release_pre  cma_free_mb=24  pid=3237 owner=llm hef=Qwen3-1.7B-Instruct.hef
2026-05-17T14:12:36+0900 event=release_post cma_free_mb=25  pid=3237 owner=llm hef=Qwen3-1.7B-Instruct.hef
```

### 1-2. Интерпретация

| Фаза | Разница CmaFree | Значение |
|---|---|---|
| `vdevice_create_pre` → `vdevice_create_post` | **+1 МБ (≈ 0)** | Создание VDevice само по себе почти не потребляет CMA |
| `acquire_pre` → `acquire_post` (загрузка Qwen3-1.7B-Instruct) | **−285 МБ** | 1 LLM потребляет 285 МБ |
| `acquire_post` → `release_pre` (6 минут инференса) | **−84 МБ / 6 мин ≒ −14 МБ/мин** | **Непрерывная утечка также во время инференса** |
| `release_pre` → `release_post` (выгрузка LLM) | **+1 МБ** | **`release()` фактически не возвращает CMA** |

### 1-3. Сравнение с предыдущей гипотезой

Это результат измерений, частично опровергающий начальную гипотезу из `SQLCIPHER_MMAP_CORRUPTION.md` §7, созданного 2026-05-16, и гипотезу старого документа о том, что «стратегия удержания VDevice (наш пустой `_maybe_reset_vdevice`) усиливает утечку». Поскольку создание VDevice = 0 МБ / release = 0 МБ, **изменение стратегии удержания (= изменение `_maybe_reset_vdevice` для сброса при каждом вызове) не дало бы никакого эффекта**.

## 2. Структурные ограничения

На основании результатов измерений, HailoRT 5.3.0 (сборка сообщества, API `hailo_platform.genai`) имеет три сосуществующих проблемы:

1. **`VDevice.release()` / `release()` модели GenAI не возвращает CMA хоста** (подтверждено измерением)
   - Внутри одного процесса драйвер PCIe (`hailo1x_pci`) продолжает удерживать DMA-области, и операция, эквивалентная `munmap`, не происходит
2. **Непрерывная утечка CMA во время инференса (~14 МБ/мин)** (подтверждено измерением)
   - Сегодняшнее наблюдение: 84 МБ потеряно за 6 минут использования Qwen3-1.7B-Instruct
   - Отдельный путь, независимый от загрузки/выгрузки. Исчерпание происходит даже без выгрузки
3. **Не подтверждён способ надёжного восстановления CMA кроме перезагрузки Pi** (измерение + отчёты сообщества)
   - Даже перезапуск серверного процесса (эквивалент `systemctl restart yu-ai-manager`) неполон, поскольку `hailo1x_pci` удерживает DMA до цикла питания PCIe. Полное восстановление требует `sudo reboot` Pi (измерено в этом репозитории)
   - В сообществе Hailo существуют несколько независимых отчётов: <https://community.hailo.ai/t/hailo-10h-on-rpi5-undocumented-api-findings-dfc-conversion-failures-with-transformer-based-models-swinv2-vit-convnext/18979> и <https://community.hailo.ai/t/hailo-10h-throughput-degrades-irreversibly-within-minutes-of-continuous-use-125-41-fps-only-host-reboot-recovers/19218> (явно указывается, что `VDevice.release()` / завершение процесса / перезагрузка драйвера не восстанавливает, только перезагрузка хоста)
   - Это уже задокументировано для пользователей в сообщении об ошибке предварительного отказа `acquire_genai` (`core/hailo_device_core/device_manager_genai.py::acquire_genai`, "a full system reboot is required")

### 2-1. «Возвращает ли убийство дочернего процесса CMA?»: **Опровергнуто измерением** (2026-05-17 Phase 0 PoC)

Предыдущая версия (rev1) теоретически заключила, что «ядро Linux восстанавливает страницы DMA при разборке `mm_struct`, поэтому убийство дочернего процесса полностью возвращает CMA», но **измерение с помощью Phase 0 PoC (`tools/diag_hailo_cma_reclaim.py`) независимо подтвердило дважды, что убийство дочернего процесса почти не возвращает CMA**.

**Результаты измерений (2-й прогон, строгая версия)**:

| Точка измерения | CmaFree | Δ |
|---|---:|---:|
| Базовая линия (до запуска PoC) | 503 МБ | — |
| После создания VDevice | 372 МБ | **-131 МБ** (конструкция VDevice потребляет CMA в дочернем процессе с холодным стартом) |
| После загрузки LLM | 372 МБ | 0 МБ (LLM содержится в пуле DMA VDevice, нет нового потребления) |
| После SIGTERM + join | 378 МБ | +6 МБ |
| **После 30 секунд ожидания** | **380 МБ** | **Всего восстановлено только +8 МБ** |

По сравнению с ожидаемым восстановлением ≥250 МБ, реальное значение составило лишь +8 МБ (+1 МБ при первом случайном измерении). Это на уровне системного джиттера — **значимого восстановления CMA не произошло**.

**Подтверждённый диагноз**:

- Драйвер `hailo1x_pci` управляет пулом DMA во **внутреннем глобальном состоянии драйвера**, а не в `mm_struct` пользовательского процесса (предположительно)
- Не восстанавливается при `process exit`, `kill` или `module unload` (согласуется с отчётами сообщества)
- **Единственный подтверждённый способ восстановления — `sudo reboot` Pi (= цикл питания PCIe)** ← это измеренный факт, указанный в §2 строке 3

Подробный отчёт: `docs/superpowers/specs/codex-reviews/2026-05-17-hailo-subprocess-isolation-phase0-poc-result.md`

В результате этих выводов `docs/superpowers/specs/2026-05-17-hailo-subprocess-isolation-design.md` помечается как **REJECTED**, и подход к смягчению через изоляцию subprocess отменяется. В качестве альтернативы принимается подход автоматической перезагрузки из §4 (D).

## 3. Операционные последствия

### 3-1. «1 модель на перезагрузку Pi» — фактический предел

- С Pi 5 (лимит CMA 512 МБ, не может быть увеличен согласно спецификации Pi) + LLM Qwen3 (285 МБ):
    - CmaFree сразу после перезагрузки ≒ 480 МБ
    - После загрузки 1 LLM → CmaFree ≒ 190 МБ
    - После нескольких десятков минут инференса → CmaFree ≒ 50 МБ или меньше
    - **Загрузка второй модели навсегда невозможна** (требует 250+ МБ, но остаток недостаточен, и release ничего не возвращает)

### 3-2. Одновременное использование LLM + VLM / LLM + S2T невозможно

- Случаи использования, чередующие VLM (на основе llava, ~300 МБ), S2T (whisper-small, ~175 МБ) и LLM, невозможны из-за вышеуказанных ограничений, если не следовать процедуре **загрузить → перезагрузить → загрузить**.
- **Мульти-модельный UX, такой как «прикрепить изображение во время разговора, чтобы переключиться на другую модель» или «транскрибировать аудио разговора», структурно невозможен с HailoRT 5.3.0**.

### 3-3. Длительные непрерывные сессии инференса затруднены

- Утечка 14 МБ/мин означает, что даже начиная с 200 МБ CmaFree, через 14 минут остаётся половина, а через 30 минут почти всё исчерпано.
- Чат-сессии продолжительностью более 30 минут не могут быть стабилизированы без промежуточной перезагрузки Pi.

| Вариант | Эффект | Трудозатраты | Побочные эффекты / Риски |

## 6. Шаги воспроизведения (для отчётов о проблемах Hailo)

Минимальные шаги воспроизведения для внешних отчётов об ошибках:

```bash
# 1. Подтвердить базовую линию сразу после перезагрузки Pi
grep CmaFree /proc/meminfo
# CmaFree: ~480000 кБ

# 2. Запустить сервер + загрузить 1-й LLM (напр.: отправить 1 сообщение через GenAI в /tools)
# 1 запрос к /api/llm/generate или /api/chat/send

# 3. Проверить CmaFree
grep CmaFree /proc/meminfo
# CmaFree: ~100 МБ (-280 МБ)

# 4. Выгрузить модель
curl -X POST http://127.0.0.1:5000/ext/hailo-genai/api/model/unload -d '{"model":"llm"}'

# 5. Проверить CmaFree
grep CmaFree /proc/meminfo
# CmaFree: ~100 МБ (не возвращено ← баг)

# 6. Попытка повторной загрузки той же / другой модели → отклонено из-за недостаточной CMA
```

Ожидаемое поведение: На шаге 5 CmaFree должна вернуться к значению, близкому к базовой линии шага 1 (>400 МБ).
Фактическое поведение: Возвращается только около +1 МБ, повторная загрузка невозможна.
