## 1. Процедура первоначального запуска и активации

### 1.1 Перезапуск сервера

Для применения изменений конфигурации необходим перезапуск. **Перезапустите тем же способом, который используется в данный момент.**

Типичная команда запуска (скорректируйте под реальную среду):

```bash
cd /home/pi/GitHub/yu_ai_manager
uv run python web_ui.py --config config.json --db data/tags.db
```

Если сервер работает как сервис systemd, перезапустите соответствующий unit командой `sudo systemctl restart <unit>`.

### 1.2 Проверка в течение 30 секунд после запуска (3 пункта)

#### A. Зафиксировано ли событие `boot_baseline`?

```bash
tail -n 20 /home/pi/GitHub/yu_ai_manager/logs/hailo_auto_reboot.log
```

Ожидается: одна строка вида `{"event":"boot_baseline","state":"idle","mode":"lazy","dry_run":true,"cma_free_mb":<int|null>,"hailo_runtime_version":"5.3.0",...}`.

**Устранение неполадок при отсутствии**:

- `logs/hailo_auto_reboot.log` не существует → цикл judge не запущен (возможно, запуск произошёл не в режиме `["full"]` или задана переменная окружения `TAGDB_DISABLE_HAILO_AUTO_REBOOT_JUDGE`)
- Файл существует, но пуст → ошибка разрешения пути в `core/hailo_device_core/auto_reboot_logger.py`; проверьте права доступа к каталогу `logs/`
- `cma_free_mb: null` → сбой чтения `/proc/meminfo` (ожидаемое поведение на оборудовании, отличном от Pi, безвредно)

#### B. Активирован ли opt-in через ответ `/api/system/cma`?

При входе через PIN в браузере API-ключ не требуется. Используйте curl или выполните в консоли DevTools браузера (при активной PIN-сессии):

```js
fetch("/ext/hailo-genai/api/system/cma").then(r => r.json()).then(j => console.log(j.cma.auto_reboot))
```

Ожидается:

```json
{
  "enabled": true,
  "mode": "lazy",
  "dry_run": true,
  "state": "idle",
  "consecutive_rejects": 0
}
```

Если `enabled: false` или `mode: "off"` → проверьте, что `hailo.auto_reboot.mode` в config.json равно `"lazy"` и что сервер полностью перезапущен.

#### C. Отсутствуют ли ошибки запуска в `error.log`?

```bash
tail -n 50 /home/pi/GitHub/yu_ai_manager/logs/error.log | grep -iE "hailo_auto_reboot|auto_reboot"
```

Отсутствие вывода означает норму. При наличии ошибок обратитесь к разделу «8. Известные ловушки» в конце документа.

## 2. Ежедневная эксплуатация в период наблюдения

### 2.1 Обычное использование

**Основное действие**:

- **Использовать LLM-чат как обычно** через `/ext/hailo-genai/chat` или `/tools` (например, Qwen3-1.7B)
- По необходимости использовать VLM / S2T
- Длительные сессии (30+ минут непрерывно) и многократное переключение моделей также стоит намеренно пробовать, чтобы расширить данные наблюдения

Специальное тестирование не требуется. **Чем нормальнее использование, тем больше данных собирает фаза 0.5** — такова цель дизайна.

### 2.2 Еженедельный обзор (раз в неделю, ~5 минут)

```bash
cd /home/pi/GitHub/yu_ai_manager

# Количество вхождений каждого типа событий
jq -r '.event' logs/hailo_auto_reboot.log | sort | uniq -c

# Временны́е метки и CmaFree для событий would_fire
grep would_fire logs/hailo_auto_reboot.log | jq -r '[.ts, .cma_free_mb] | @tsv'

# Причина drain_entered (cma или rejects)
grep drain_entered logs/hailo_auto_reboot.log | jq -r '[.ts, .cma_free_mb, .consecutive_rejects, .reason] | @tsv' 2>/dev/null || \
  grep drain_entered logs/hailo_auto_reboot.log | head -10
```

**Контрольные точки**:

- `would_fire` встречается 1 или более раз → внедрение фазы 1 оправдано (проверьте, совпадают ли зафиксированные временны́е метки с моментами ручных перезагрузок)
- `prewarn_entered` срабатывает часто, но не переходит в `drain_entered` → `prewarn_threshold_mb` (80 МБ) может быть слишком низким; откалибруйте заново
- Причина `drain_entered` всегда `rejects` → DRAIN вызывается отказами; нужны меры, отличные от корректировки порогов

## 3. Завершение наблюдения и критерии перехода к фазе 1

### 3.1 Необходимый период наблюдения

**Минимум 7 дней / Рекомендуется 14 дней**. Период должен охватывать как минимум следующие сценарии:

- Обычный LLM-чат
- Длительный непрерывный LLM-чат (30+ минут в одной сессии)
- Переключение моделей VLM / S2T
- Как минимум один предварительный отказ `acquire_genai` (недостаточно CmaFree)
- Первая загрузка после перезагрузки Pi

### 3.2 Числовые критерии внедрения фазы 1

Сводка:

```bash
cd /home/pi/GitHub/yu_ai_manager
jq -r '.event' logs/hailo_auto_reboot.log | sort | uniq -c
```

Таблица решений:

| Результат наблюдения | Решение по фазе 1 |
|---|---|
| `would_fire` ≥ 1 | **GO** (автоматическая перезагрузка имеет ценность) |
| `would_fire` = 0, `drain_entered` ≥ 1 | Скорректировать пороги и рассмотреть фазу 1 (DRAIN достигается, но `would_fire` нет — `fire_grace_seconds` можно сократить) |
| Только `prewarn_entered`, `drain_entered` = 0 | При текущих порогах «критическое» состояние ни разу не достигается → фаза 1 может не понадобиться в зависимости от паттернов использования |
| Все события 0 (только `boot_baseline`) | Использование не исчерпывает CMA → фаза 1 не нужна |

### 3.3 Задачи после завершения наблюдения

1. Сохранить сводные результаты в `docs/ru/hailo/HAILO_AUTO_REBOOT_PHASE05_OBSERVATION_RESULTS.md` (новый файл)
2. При внедрении фазы 1: перейти к фазе 1 в спецификации rev3 §5.2 (UI-баннер DRAIN + i18n); пересмотреть пороги §3.1 на основе данных наблюдения
3. Если фаза 1 не нужна: установить `mode = "off"` в config.json и архивировать журнал наблюдения

## 4. Процедура отключения (в аварийной ситуации / при остановке наблюдения)

```bash
cd /home/pi/GitHub/yu_ai_manager
jq '.hailo.auto_reboot.mode = "off"' config.json > config.json.tmp && mv config.json.tmp config.json
# Перезапустить сервер
```

Даже при `mode = "off"` события JSONL продолжают фиксироваться (вывод WARN в `error.log` подавляется). Для полного отключения используйте переменную окружения:

```bash
TAGDB_DISABLE_HAILO_AUTO_REBOOT_JUDGE=1 uv run python web_ui.py ...
```

## 8. Известные ловушки

| Симптом | Причина и решение |
|---|---|
| В `logs/hailo_auto_reboot.log` ничего нет | Сервер не перезапущен / `mode = "off"` по-прежнему установлен / запуск не в режиме `["full"]` / задана переменная окружения `TAGDB_DISABLE_HAILO_AUTO_REBOOT_JUDGE` |
| `cma_free_mb: null` не прекращается | Запуск на оборудовании, отличном от Pi (например, WSL2), или сбой чтения `/proc/meminfo`; повторно проверьте на реальном оборудовании Pi |
| `hailo_runtime_version: null` | Пакет `hailo_platform` не установлен в данной среде; на реальном Pi 5 значение заполняется при наличии среды выполнения HailoRT 5.3.0 |
| `would_fire` не появляется ни разу | Нагрузка использования слишком мала или пороги слишком широкие; попробуйте длительный непрерывный чат / переключение моделей и повторите наблюдение |
| Режим `eager` настроен, но не работает | В фазе 0.5 `eager` намеренно откатывается к `off` (с записью предупреждения в журнал); реализация запланирована в фазе 1+ |
