# Продолжение по DFC: Повторная проверка моделей WD-Tagger в DFC v5.3.0

**Дата**: 2026-04-06
**Версия DFC**: 5.3.0
**Предыдущий отчёт**: [`ONNX_TO_HEF_CONVERSION_REPORT.md`](ONNX_TO_HEF_CONVERSION_REPORT.md) (2026-03-06)
**Среда**: WSL2 (Ubuntu 24.04), x86_64

---

## Предыстория

В марте 2026 года было задокументировано, что три варианта WD-Tagger (SwinV2, ViT, ConvNeXt)
потерпели сбой на этапе парсера Hailo Dataflow Compiler v5.2.0, не дойдя до шага квантования.
Исходный отчёт хранится в [`ONNX_TO_HEF_CONVERSION_REPORT.md`](ONNX_TO_HEF_CONVERSION_REPORT.md).

После выхода DFC v5.3.0 те же три модели были проверены повторно. Результаты записаны здесь.

---

## Сводка результатов

| Модель | Размер | Ошибка DFC 5.2.0 | Ошибка DFC 5.3.0 | Изменение |
|--------|--------|-------------------|-------------------|-----------|
| `wd-swinv2-tagger-v3` | 446 МБ | `_convert_axes_to_nhwc` `IndexError` | То же | **Нет** |
| `wd-vit-tagger-v3` | 362 МБ | То же | То же (даже после повтора через onnxsim) | Только добавлен поток повтора |
| `wd-convnext-tagger-v3` | 377 МБ | `UnsupportedShuffleLayerError` | То же + добавился `UnsupportedModelError` | **Ошибок стало больше** |

**Все три модели по-прежнему завершаются сбоем на этапе парсера.** Шаг квантования с
500 подготовленными калибровочными изображениями так и остаётся недостижимым, как и в v5.2.0.

---

## Что изменилось в DFC v5.3.0

Хотя сбои продолжаются, по сравнению с v5.2.0 наблюдаются следующие улучшения:

### 1. Добавлен метод `_create_layer_normalization_layer`

Этот метод отсутствовал в v5.2.0. В DFC v5.3.0 делается попытка явно обработать
оператор `LayerNormalization` в специальном пути кода. Это явный признак прогресса в разработке.

Однако **внутренняя реализация ещё не завершена** — после вызова метода следующий вызов
`_convert_axes_to_nhwc` выбрасывает `IndexError: list index out of range` на той же форме
тензора, что и в v5.2.0.

### 2. Добавлен поток упрощения через onnxsim с повтором

Для ViT и ConvNeXt DFC v5.3.0 теперь автоматически упрощает входной ONNX через `onnxsim`
и повторяет парсинг. Упрощённая модель сохраняется рядом с исходной как `model.sim.onnx`.
Это полезная сетка безопасности для моделей с избыточными ONNX-графами.

Для текущих моделей, однако, первопричина находится на стороне `_convert_axes_to_nhwc`,
поэтому повтор тоже **завершается сбоем в той же точке**.

### 3. Рекомендация end-узлов

Для ConvNeXt DFC v5.3.0 теперь рекомендует конкретные end-узлы при отказе парсера
и предлагает пользователю закрепить их и повторить попытку.

Повтор с рекомендованными end-узлами также завершается сбоем — первопричина в обработке
LayerNormalization / Transpose, а не в выборе end-узла.

---

## Первопричина (без изменений с марта)

ONNX-парсер DFC по-прежнему не может выполнить преобразование осей оператора `LayerNormalization`,
когда входной тензор не соответствует ожидаемому формату NCHW. Цепочка вызовов:

```
_create_layer_normalization_layer
  → get_layer_normalization_info
    → _convert_axes_to_nhwc
      → IndexError: list index out of range
```

Для ConvNeXt дополнительно наблюдается `UnsupportedShuffleLayerError` на нескольких
узлах Transpose (`token_5` ~ `token_34`), что свидетельствует о неполной обработке
Transpose-паттернов channels-last в этой архитектуре.

Новый код существует, но он пока не справляется с ранее проваливавшимися случаями.

---

## Пожелания (без изменений с марта)

### 1. Исправить `_convert_axes_to_nhwc` для многомерного `LayerNormalization`

До метода теперь дотягиваются (улучшение). Но логика отображения осей сама по себе
не работает для тензоров не-NCHW. Это необходимо для SwinV2, ViT, ConvNeXt и большинства
Transformer-архитектур последних лет.

### 2. ONNX Runtime Execution Provider для Hailo-10H

Это структурно решило бы данный класс проблем, сделав полную конвертацию DFC необязательной.

---

## О компоненте «ONNX Runtime Hailo Pipeline»

В примечаниях к выпуску DFC v5.3.0 упоминается компонент «ONNX Runtime Hailo Pipeline».
Если этот компонент позволит выполнять инференс WD-Tagger на Hailo-10H без полной конвертации DFC
(то есть как Execution Provider ORT, делегирующий только поддерживаемые подграфы на NPU),
было бы очень полезно официальное руководство по его правильному использованию.

Конкретно:
- Предназначен ли этот компонент как путь продвижения для моделей, которые DFC пока не может распарсить?
- Нужен ли частичный HEF (скомпилировать поддерживаемые подграфы в HEF, остальное через ORT на CPU)?
- Есть ли пример кода или туториал для Transformer-ONNX моделей?

## Шаги воспроизведения

```bash
# 1. Настроить чистый Python venv с DFC v5.3.0
python3.11 -m venv venv
source venv/bin/activate
pip install hailo_dataflow_compiler-5.3.0-py3-none-linux_x86_64.whl

# 2. Скачать 3 варианта WD-Tagger ONNX
for variant in swinv2 vit convnext; do
  huggingface-cli download \
    "SmilingWolf/wd-${variant}-tagger-v3" \
    model.onnx --local-dir "./wd-${variant}-tagger-v3"
done

# 3. Попробовать парсинг для каждой модели
for variant in swinv2 vit convnext; do
  hailo parser onnx "./wd-${variant}-tagger-v3/model.onnx" \
    --hw-arch hailo10h \
    --tensor-shapes input_1:1,448,448,3 2>&1 | tee "${variant}_5.3.0.log"
done
```

## Итог

Усилия разработки, видимые в DFC v5.3.0 (`_create_layer_normalization_layer`,
поток повтора через onnxsim, рекомендации end-узлов), по-настоящему обнадёживают.
Это именно тот прогресс, который ожидало сообщество. Оставшийся пробел — в самой
реализации `_convert_axes_to_nhwc`, которая теперь достижима, но пока не работает
для текущих моделей.

Повторные проверки будут продолжаться с каждым релизом DFC. Если сотрудникам Hailo
нужны полные логи ошибок, SHA-256 хэши ONNX-моделей и минимальный код воспроизведения,
они будут предоставлены с удовольствием.
