# Ограничения CMA на Raspberry Pi 5 при `numa=fake=8`

Практические сведения о выделении CMA на Raspberry Pi 5 (8 ГБ) при выполнении нагрузок Hailo-10H.
Описывает предел `cma=`, причину, по которой значения выше 512M отказывают молча, и способ восстановления CMA, занятого драйвером дисплея.

**Целевая аудитория**: разработчики, запускающие модели Hailo GenAI (LLM, Speech2Text) на Raspberry Pi 5
(с использованием AI HAT / AI HAT+).

---

## ⚠️ Внимание: регрессия firmware 2026-05

**Начиная с релиза `raspi-firmware 1:1.20260513-1` + `pieeprom-2026-05-11` от 2026-05-13**, запись `cma=` в `/boot/firmware/cmdline.txt` — независимо от значения — полностью «замолкает» mailbox VC firmware (`vcgencmd ioctl_set_msg failed:-1`, `raspberrypi-clk -22`, HEVC `-517`, отсутствие sysfs cpufreq).

**Подтверждённый рекомендуемый способ с 2026-05-16**: вместо cmdline `cma=` — записать `dtoverlay=cma,cma-512` в `/boot/firmware/config.txt`. Память выделяется через reserved memory node `linux,cma` в DT, что не конфликтует с новым firmware. Подробности см. в §6 и [`docs/development/investigations/pi5_firmware_cma_mailbox_regression_2026-05-16.md`](../../development/investigations/pi5_firmware_cma_mailbox_regression_2026-05-16.md).

Приведённое ниже старое описание (рекомендация cmdline `cma=512M`) — результат проверки по состоянию на 2026-04-15. Вывод о верхнем пределе (512M), обусловленном границей узла NUMA, по-прежнему верен, но **место настройки перенесено с cmdline на аргумент overlay в config.txt**.

## TL;DR

- **Место настройки — `dtoverlay=cma,cma-512` в `config.txt`** (подтверждено 2026-05-16; cmdline `cma=` ломает mailbox на новом firmware)
- `cma-1024` и `cma-768` на Pi 5 (8 ГБ) **отказывают молча** — `CmaTotal` становится 0, без паники ядра и без предупреждений (предел обусловлен границей узла NUMA; предполагается, что то же ограничение сохраняется и через overlay)
- **`cma-512` — подтверждённый предел и рекомендуемое значение** (повторно проверено через overlay 2026-05-16 на Pi 5 8 ГБ, подтверждено выделение `CmaTotal: 524288 kB`)
- Первопричина: ядро Pi 5 по умолчанию применяет `numa=fake=8`, ограничивая непрерывное выделение памяти одним узлом NUMA (1 ГБ)
- **`dtoverlay=vc4-kms-v3d` + `max_framebuffers=2` потребляют ~157 МБ CMA при загрузке** — даже если инициализация драйвера DRM завершается неудачей (проверено 2026-04-15)
- **`camera_auto_detect=1`** загружает `pisp_be` и `videobuf2_dma_contig`, потребляя дополнительный CMA. На headless-системах рекомендуется отключить
- **Базовая линия headless-оптимизации** (обе overlay отключены): ~98 МБ CMA используется при загрузке, ~414 МБ свободно для моделей Hailo
- **YOLO InferModel использует 0 МБ CMA** (подтверждено 2026-04-15) — из CMA выделяются только модели GenAI (LLM, Speech2Text)
- Одновременная загрузка LLM (qwen2.5-1.5b) + Whisper-base: суммарно ~328 МБ — укладывается в базовую линию headless-оптимизации
- CMA не освобождается при перезапуске сервера — освобождается только при полной перезагрузке системы (повторная подача питания PCIe) (баг драйвера `hailo1x_pci`, зарегистрирован у Hailo)
- Обращайтесь с VDevice как с **синглтоном на весь жизненный цикл процесса**. Вытеснение/перезагрузка запрещены

## 1. Симптомы

При установке `cma=1G` (или `cma=768M`) в `/boot/firmware/cmdline.txt` и перезагрузке наблюдается следующее:

```
$ grep CmaTotal /proc/meminfo
CmaTotal:              0 kB
```

Система загружается нормально. Нет паники ядра, нет сообщений об ошибке. Настройка CMA в `cmdline.txt` **молча игнорируется**, и всё, что зависит от CMA (NPU Hailo-10H, камеры V4L2 и т. д.), не может инициализироваться.

**После каждого изменения `cmdline.txt` всегда проверяйте выделение CMA:**

```bash
grep CmaTotal /proc/meminfo
```

## 2. Первопричина: граница узла `numa=fake=8`

Ядро Raspberry Pi OS по умолчанию для Pi 5 применяет `numa=fake=8`, разбивая 8 ГБ физической памяти на **8 виртуальных узлов NUMA по 1 ГБ каждый**:

```
numa=fake=8 physical memory layout (8 GB total):

┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ 1GB  │ 1GB  │ 1GB  │ 1GB  │ 1GB  │ 1GB  │ 1GB  │ 1GB  │
│node0 │node1 │node2 │node3 │node4 │node5 │node6 │node7 │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
```

Linux CMA (`cma_init_reserved_mem`) при загрузке должна выделяться как **непрерывная физическая память, не пересекающая границу узла NUMA**.
Это накладывает жёсткий предел в 1 ГБ на узел. Поскольку само ядро занимает часть памяти того же узла, зарезервировать ровно 1 ГБ невозможно:

> **Приведённая ниже таблица — запись измерений по состоянию на 2026-04-15 для cmdline-способа.**
> Вывод о предельном значении (512M), обусловленном границей узла NUMA, по-прежнему верен, но **cmdline `cma=` больше использовать нельзя** (см. регрессию firmware в начале документа).
> Актуальный способ настройки — `dtoverlay=cma,cma-512` в `config.txt` (§6).

| Настройка `cmdline.txt` (запись по состоянию на 2026-04-15) | Результат |
|---|---|
| `cma=1G` | Пытается занять весь узел целиком. Не остаётся места для ядра → **молчаливый отказ**, CmaTotal=0 |
| `cma=768M` | Превышает надёжный непрерывный диапазон → **молчаливый отказ**, CmaTotal=0 (проверено 2026-04-15) |
| `cma=512M` | Половина узла → **подтверждённо стабильно** ✓ (проверено 2026-04-15) ← рекомендация того времени. **Сейчас используйте `dtoverlay=cma,cma-512`** |
| `cma=384M` | Не проверялось (512M подтверждено; 384M не требуется) |
| `cma=256M` | Стабильно, но тесно при одновременном использовании LLM + Whisper |
| `cma=128M` | Стабильно, но недостаточно для Hailo GenAI (одному LLM требуется ~234 МБ) |

### Почему отказ происходит молча

`cma_init_reserved_mem` не вызывает панику при неудачном выделении. Ядро загружается с `CmaTotal=0`, как будто CMA вообще не запрашивался.
Значение, записанное в `cmdline.txt`, фактически игнорируется.

## 3. Требования Hailo-10H к CMA

Измерено на Raspberry Pi 5, AI HAT+, HailoRT 5.3.0:

| Модель / комбинация | Использование CMA | Примечание |
|---|---|---|
| LLM — qwen2.5-1.5b-chat (отдельно) | **~234 МБ** | измерено 2026-04-15 |
| YOLO InferModel (yolov8n, configure + bindings) | **0 МБ** | подтверждено 2026-04-15 |
| Whisper-tiny (отдельно) | ~70 МБ | оценка |
| Whisper-base (отдельно) | ~100 МБ | оценка |
| Whisper-small (отдельно) | ~150 МБ | оценка |
| **LLM + Whisper-tiny (одновременно)** | **~246 МБ** | измерено при CMA 256 МБ |
| **LLM + Whisper-base (одновременно)** | **~334 МБ** | оценка. Ожидается, что уложится в headless-базовую линию |

**YOLO использует 0 МБ CMA**: в HailoRT 5.3.0 YOLO InferModel, `configure()` и `create_bindings()` вообще не выделяют CMA.
Буферы DMA для входа и выхода отображаются из заранее выделенных массивов numpy через `set_buffer()`, а не из CMA.
Поэтому YOLO не учитывается в расчёте бюджета CMA.

При применении headless-оптимизации с CMA 512 МБ (см. §5) ожидается, что будут работать следующие конфигурации:

- Только LLM (~234 МБ, запас ~180 МБ)
- Только Whisper-tiny / Whisper-base (укладывается легко)
- LLM + Whisper-base одновременно (суммарно ~334 МБ, запас ~80 МБ)

Комбинация Whisper-small и LLM (оценочно ~384 МБ) приближается к теоретическому пределу — прежде чем доверять этому значению, проверьте его реальными измерениями.

Подробности о результатах тестов одновременной загрузки см. в [hailo_genai_concurrent_2026-04-15.md](../../development/investigations/hailo_genai_concurrent_2026-04-15.md).

## 4. CMA не освобождается до полной перезагрузки

CMA, выделенный HailoRT, остаётся занятым в памяти до полной перезагрузки системы.
Это не меняется независимо от `VDevice.release()`, завершения серверного процесса или перезагрузки модуля ядра.

**Первопричина** (подтверждено 2026-04-15): `hailo1x_pci` сохраняет DMA-когерентные выделения даже после закрытия fd устройства или перезагрузки модуля.
Освобождение происходит только при полной перезагрузке (повторной подаче питания PCIe). Баг зарегистрирован у Hailo.

| Фаза | CmaFree (CMA 512 МБ, headless-оптимизация) |
|---|---|
| Загрузка | **~426 МБ** |
| После загрузки LLM (~234 МБ) | ~192 МБ |
| После загрузки Whisper-base (~100 МБ) | ~92 МБ |
| После `VDevice.release()` | ~92 МБ (**не возвращается**) |
| После завершения серверного процесса | ~92 МБ (**не возвращается**) |
| После `rmmod hailo1x_pci && modprobe hailo1x_pci` | ~92 МБ (**не возвращается**) |
| После полной перезагрузки системы | **~426 МБ (восстановлено)** |

**Вывод**: потребление CMA накапливается в рамках одной загрузочной сессии, переживая перезапуски сервера.
Не рассчитывайте на освобождение CMA при перезапуске сервера. Проектируйте VDevice как **синглтон на весь жизненный цикл процесса**.
Если CMA исчерпан, восстановить его можно только полной перезагрузкой системы.

## 5. Headless-оптимизация: `/boot/firmware/config.txt`

Стандартный `config.txt` Pi OS содержит два параметра, которые потребляют значительный объём CMA даже на headless-системах (без дисплея).

### 5.1 `dtoverlay=vc4-kms-v3d` и `max_framebuffers=2`

**Эффект**: firmware Pi 5 заранее выделяет CMA-фреймбуферы для конвейера отображения при загрузке.
При `max_framebuffers=2` это потребляет ~157 МБ CMA **ещё до запуска пользовательских процессов**.

Выделение сохраняется даже если драйвер Linux DRM позже завершится неудачей при инициализации (например, `[drm] Couldn't stop firmware display driver: -22` или `Couldn't get core clock` в `dmesg`).

| Состояние `config.txt` | CmaFree при загрузке |
|---|---|
| `dtoverlay=vc4-kms-v3d` + `max_framebuffers=2` включены (по умолчанию) | **~257 МБ** |
| Оба закомментированы | **~305 МБ** (+~48 МБ) |

**Исправление** (для headless / серверного режима):

```ini
# /boot/firmware/config.txt
#dtoverlay=vc4-kms-v3d
#max_framebuffers=2
```

**Компромисс**: `vc4-kms-v3d` необходим для аппаратно ускоренного вывода изображения и 3D (V3D).
Если доступ к системе осуществляется только через SSH или веб-интерфейс, отключение безопасно.

### 5.2 `camera_auto_detect=1` и `display_auto_detect=1`

**Эффект**: эти overlay при загрузке опрашивают CSI-камеры и DSI-дисплеи, загружая `pisp_be` (бэкенд Pi ISP) и `videobuf2_dma_contig`.
Загруженные модули и обнаруженное оборудование заранее выделяют дополнительный CMA.

| Состояние `config.txt` | CmaFree при загрузке |
|---|---|
| `camera_auto_detect=1` + `display_auto_detect=1` | ~305 МБ (после отключения vc4) |
| Оба установлены в 0 | **~426 МБ** (+~121 МБ) |

**Исправление**:

```ini
camera_auto_detect=0
display_auto_detect=0
```

**Примечание**: `camera_auto_detect=0` влияет только на CSI-камеры. USB-камеры (UVC / `uvcvideo`) не затрагиваются и продолжают работать нормально.

### 5.3 Рекомендуемый минимальный `config.txt` для headless AI HAT+

```ini
auto_initramfs=1
arm_64bit=1
arm_boost=1

[cm5]
dtoverlay=dwc2,dr_mode=host

[all]
dtparam=pciex1_gen=3
```

Оценочное использование CMA при загрузке с этой конфигурацией: **~98 МБ занято**, ~414 МБ свободно для моделей Hailo.

### 5.4 Сводка бюджета CMA (CMA 512 МБ, headless-оптимизация)

| Конфигурация | CmaFree | Доступно для Hailo |
|---|---|---|
| По умолчанию (vc4-kms-v3d + камера включены) | ~257 МБ | ~257 МБ |
| vc4-kms-v3d + max_framebuffers отключены | ~305 МБ | ~305 МБ |
| + camera/display_auto_detect=0 | **~426 МБ** | **~426 МБ** |
| После загрузки LLM (~234 МБ) | ~192 МБ | для Whisper |
| После загрузки LLM + Whisper-base (~100 МБ) | ~92 МБ | (запас) |

## 6. Рекомендуемая конфигурация

### Настройка `dtoverlay=cma,cma-512` (подтверждено 2026-05-16)

```bash
# Проверить текущее состояние CMA
grep CmaTotal /proc/meminfo

# 1) Удалить существующий cma= из cmdline.txt (ломает mailbox на новом firmware)
sudo sed -i 's/ *cma=[^ ]*//g' /boot/firmware/cmdline.txt

# 2) Добавить dtoverlay=cma,cma-512 в секцию [all] файла config.txt
sudo sed -i '/^\[all\]$/a dtoverlay=cma,cma-512' /boot/firmware/config.txt

# 3) Рекомендуется холодная перезагрузка (отключить и снова подключить питание)
sudo sync && sudo poweroff

# Проверить после перезагрузки (все 4 пункта обязательны)
vcgencmd version                                # обязателен ответ Broadcom (молчание = сбой)
grep CmaTotal /proc/meminfo                     # ожидается 524288 kB
journalctl -b -k | grep 'linux,cma'             # должно появиться "initialized node linux,cma"
journalctl -b -k | grep '0x00030087'            # не должно появляться
```

Если в dmesg встречается `OF: reserved mem: initialized node linux,cma, compatible id shared-dma-pool` — это подтверждение того, что память выделена через путь DT.
Если, наоборот, встречается `Reserved memory: bypass linux,cma node, using cmdline CMA params instead` — значит, в cmdline всё ещё остался `cma=`, и его нужно удалить.

### Если требуется включить `vc4-kms-v3d`

Если необходим дисплейный KMS DRM, его можно объединить в виде аргумента overlay:
```ini
dtoverlay=vc4-kms-v3d,cma-512
```
Однако, как указано в §5.1, `vc4-kms-v3d` потребляет ~157 МБ CMA, поэтому для задач Hailo GenAI рекомендуется его отключение.

### Проверка после каждого изменения ядра / firmware / конфигурации

После изменений `/boot/firmware/cmdline.txt` или `config.txt`, а также после обновления ядра/firmware, состояние CMA и ответ mailbox могут молча измениться.
Сделайте проверку по указанным выше 4 пунктам обязательной рутиной после каждой перезагрузки.

## 7. Взаимодействие с другими проблемами `numa=fake=8`

`numa=fake=8` вызывает как минимум две разные проблемы, связанные с этим проектом:

| Проблема | Симптом | Первопричина |
|---|---|---|
| Молчаливый отказ CMA | `CmaTotal=0` после `cma=1G`, `cma=768M` | Граница узла NUMA ограничивает непрерывное выделение |
| Сбой установки Node.js | Установщик npm/node прерывается с ошибкой памяти | Память на узел NUMA (1 ГБ) ошибочно определяется как общий объём RAM. Зарегистрировано выше по потоку как [anthropics/claude-code#33864](https://github.com/anthropics/claude-code/issues/33864) |
| Отток CMA `vc4-kms-v3d` | ~157 МБ потребляется при загрузке. Не возвращается, даже если инициализация DRM неудачна | `max_framebuffers=2` заставляет firmware резервировать CMA-фреймбуферы до запуска драйвера Linux |

И молчаливый отказ, и отток CMA от vc4 связаны с одним и тем же фундаментальным ограничением (DMA-зона в нижних 4 ГБ, граница узла NUMA).
При возникновении неожиданных проблем, связанных с памятью, сначала проверьте `/proc/meminfo` и `config.txt`.

## 8. Контрольный список быстрой диагностики

```bash
# 1. Ответ mailbox (первоочередная проверка на новом firmware)
vcgencmd version                     # молчание = подозрение, что cma= осталось в cmdline

# 2. Проверить выделение CMA
grep CmaTotal /proc/meminfo          # 0 kB = молчаливый отказ

# 3. Проверить путь DT vs путь cmdline
journalctl -b -k | grep 'linux,cma'
# Ожидается: "initialized node linux,cma, compatible id shared-dma-pool" (путь DT = нормально)
# Плохо:     "bypass linux,cma node, using cmdline CMA params instead" (остался cmdline)

# 4. Проверить топологию NUMA
numactl --hardware                   # показывает число узлов и память на узел

# 5. Проверить текущую командную строку и настройку overlay
cat /boot/firmware/cmdline.txt       # убедиться, что cma= отсутствует
grep '^dtoverlay=cma' /boot/firmware/config.txt   # dtoverlay=cma,cma-512 должен присутствовать

# 6. Проверить доступность устройства Hailo
ls /dev/h1x-*                        # HailoRT 5.3.0: /dev/h1x-0
hailortcli fw-control identify       # убедиться, что NPU доступен

# 7. Проверить config.txt на предмет потребителей CMA
grep -E 'vc4-kms-v3d|camera_auto_detect|display_auto_detect|max_framebuffers' \
  /boot/firmware/config.txt

# 8. Проверить загруженные модули ядра (пользователи CMA)
lsmod | grep -E 'vc4|v3d|pisp|videobuf2_dma'
```

**Среда проверки**: Raspberry Pi 5 8 ГБ, Raspberry Pi OS
(Linux 6.12.62+rpt-rpi-2712, aarch64), HailoRT 5.3.0, AI HAT+, CMA=512M
(**повторная проверка 2026-05-16**: Linux 6.18.29+rpt-rpi-2712 / raspi-firmware 1:1.20260513-1 / pieeprom-2026-05-11 / Hailo-10H AI HAT — выделено 524288 kB через `dtoverlay=cma,cma-512`, ответ mailbox подтверждён)
