# API 보안 지침

API 엔드포인트를 추가하거나 변경할 때마다 이 문서를 사용하세요.

## 첫 번째 의사결정

모든 엔드포인트는 다음 중 하나로 미리 분류되어야 합니다:

- `public`
- `session/user`
- `admin`
- `localhost-only`

확실하지 않으면 `admin`을 선택하세요.

## 핵심 규칙

1. `GET`이 안전하다고 가정하지 마세요.
2. `read-only API keys`는 간단한 읽기 전용입니다.
3. 내부 경로, 인벤토리, 기록, 콘텐츠, 로그 및 분석 결과는 `admin`입니다.
4. Localhost 확인은 프록시 인식 헬퍼를 사용해야 합니다.
5. 구성 엔드포인트는 허용 목록과 엄격한 유효성 검사가 필요합니다.
6. 비밀은 암호화되고 공유 헬퍼를 통해 숨겨져야 합니다.

## 읽기 전용 키에 안전하지 않음

- 내부 경로
- 파일/멤버 ID 인벤토리
- 프롬프트, 주석, 스크립트, 채팅 로그
- OCR / 분석 결과
- 큐, 기록, 감사, 승인, 스케줄러, 스캔 오류 상태
- 확장 / 프로필 / 백업 / 웹훅 / 비밀 백엔드 상태
- 저장된 타사 자격증명으로 가져온 결과

## Localhost 확인

직접 사용하지 마세요:

```
request.remote_addr == "127.0.0.1"
```

대신 기존 헬퍼를 사용하세요:

- `get_client_ip()`
- `is_local_request()`
- `is_loopback_request()`

## 구성 엔드포인트 규칙

필수:

- 키 허용 목록
- 엄격한 유형 검증
- 범위 / 열거 / URL 검증
- 읽기 시 비밀 숨기기
- 비밀에 대한 암호화된 저장

금지:

- 맹목적 `config.update(...)`
- 요청 부울에 대한 `bool(value)`
- 비밀 처리를 우회하는 일반적인 병합

## 비밀

- 현재 비밀 값을 절대 반환하지 마세요
- 목록 엔드포인트에 토큰/헤더/비밀 blob을 포함하지 마세요
- 기존 비밀을 마스킹된 자리표시자로 덮어쓰지 마세요
- 항상 전용 저장소 또는 공유 헬퍼를 사용하세요

## API의 아웃바운드 요청

`GET` 엔드포인트에서 업스트림 프로브 또는 발견 가져오기를 수행하지 마세요.

불가피한 경우:

- `admin` 필요
- 제한 시간을 짧게 유지
- localhost / 개인 IP / 메타데이터 대상 차단

## 최소 테스트

민감한 엔드포인트의 경우 다음을 추가하세요:

1. `read-only key -> 403`
2. `admin key -> 200`
3. `invalid input -> 400`
4. 비밀 숨기기 확인
5. 관련된 프록시 인식 localhost 회귀 테스트

## 검토 체크리스트

- 이 `GET`이 공개/읽기 전용 액세스에 정말 안전합니까?
- 경로, 인벤토리, 프롬프트, 스크립트, 기록 또는 원본 메타데이터를 노출합니까?
- 비밀을 유출합니까?
- 프록시 인식 헬퍼를 사용합니까?
- 암묵적 부울 강제를 피합니까?
- 맹목적 구성 병합을 피합니까?
- 의도하지 않은 아웃바운드 요청을 피합니까?
- 관리자 범위 회귀 테스트를 포함합니까?

기본 정책: 좁게 시작한 다음 필요할 때만 의도적으로 엽니다.
