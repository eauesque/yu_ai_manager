# 성능 튜닝 가이드

10만 파일 이상을 관리하는 환경에서 YU AI Manager를 쾌적하게 사용하기 위한 튜닝 가이드입니다.
기본 설정으로도 많은 최적화가 자동으로 동작하지만, 환경에 맞춰 조정하면 더욱 개선할 수 있습니다.

---

## 1. 권장 하드웨어

| 항목 | 최소 요건 | 권장 (10만 파일 이상) |
|------|---------|----------------------|
| CPU | 2코어 | 4코어 이상 (썸네일 생성이 병렬화됩니다) |
| RAM | 4 GB | 8 GB 이상 |
| 스토리지 | HDD | **SSD를 강력히 권장** — 데이터베이스 응답 속도에 직결됩니다 |
| 네트워크 | — | LAN 경유로 사용하는 경우 1 Gbps 이상 |

**특히 중요**: 데이터베이스 파일 (`data/tags.db`)은 반드시 SSD에 배치해 주세요.
이미지 파일 본체는 HDD여도 문제없지만, DB가 HDD에 있으면 검색/브라우징이 현저히 느려집니다.

---

## 2. 첫 스캔 최적화

### 스캔 루트 분할

대량의 파일을 한 번에 스캔하면 시간이 오래 걸립니다.
Settings > Scan Roots에서 스캔 루트를 여러 개로 나누어 등록하고 단계적으로 스캔하는 것을 권장합니다.

- 먼저 가장 자주 사용하는 폴더를 우선 스캔합니다
- 나머지 폴더는 스캔 큐에 추가합니다 (자동으로 순서대로 처리됩니다)
- 동일 폴더를 중복 등록해도 자동으로 감지하여 건너뜁니다

### 스캔 중에도 브라우징 가능

스캔 중에도 검색이나 썸네일 표시는 정상적으로 사용할 수 있습니다.
내부적으로 읽기 전용 데이터베이스 연결을 사용하므로 스캔의 쓰기 처리가 브라우징을 차단하지 않습니다.

### 스캔 완료 후 자동 최적화

스캔 완료 시 데이터베이스의 통계 정보가 자동 업데이트 (ANALYZE)됩니다.
이를 통해 검색 쿼리의 실행 계획이 최적화되어 이후의 검색이 빨라집니다.
특별한 조작은 필요 없습니다.

---

## 3. 브라우징 속도 개선

### Service Worker 캐시

브라우저의 Service Worker가 다음 콘텐츠를 자동 캐싱합니다:

| 종류 | 캐시 상한 | 효과 |
|------|---------|------|
| 썸네일 | 5,000건 | 2번째 이후의 그리드 표시가 즉시 |
| 프리뷰 (1200px) | 200건 | 모달 표시 가속화 |
| 원본 이미지 | 50건 | 최근 본 이미지의 재표시가 즉시 |

Service Worker는 브라우저가 자동 관리하므로 특별한 설정은 필요 없습니다.
캐시를 비우고 싶은 경우, 브라우저의 개발자 도구 > Application > Storage에서 조작할 수 있습니다.

### 가상 스크롤 활성화

수천 건의 검색 결과를 표시하는 경우, 가상 스크롤을 활성화하면 렌더링 성능이 대폭 개선됩니다.

**활성화 절차**: Settings > Appearance > 「Virtual Scroll」을 ON

가상 스크롤은 화면에 보이는 범위의 카드만 DOM에 렌더링하므로 메모리 사용량과 렌더링 부하가 크게 경감됩니다.
수만 건 규모의 라이브러리에서는 활성화를 강력히 권장합니다.

### WebP 썸네일

썸네일은 WebP 형식으로 생성됩니다 (JPEG 대비 30-40% 작음).
이를 통해 전송량이 절감되며, 특히 LAN 경유 접속에서 효과를 발휘합니다.
설정 불요, 자동으로 적용됩니다.

## 4. 검색 성능

### 인덱스의 효과

데이터베이스에는 주요 검색 패턴에 최적화된 인덱스가 자동 생성되어 있습니다.
날짜순 정렬, 태그 필터, 경로 검색 등이 고속으로 동작합니다.

**기준값**:
- 필터 없는 검색: 28만 건 규모에서도 응답 50ms 이내
- 태그 필터 포함 검색: 100ms 이내
- 경로 검색 (FTS5): 50ms 이내

### FTS5 전문 검색 vs LIKE 검색

경로 검색에는 FTS5 (Full-Text Search) 인덱스가 자동으로 사용됩니다.
기존 LIKE 검색 (`%keyword%`)과 비교하여 20-100배 빠릅니다.

FTS5를 사용할 수 없는 경우 (이전 DB에서 업그레이드한 경우 등) 자동으로 LIKE 검색으로 폴백합니다.
스캔을 1회 실행하면 FTS5 인덱스가 구축됩니다.

**일본어 검색 참고**: 한자/히라가나/가타카나를 포함한 검색은 내부적으로 LIKE 폴백이 사용되는 경우가 있습니다.
이는 SQLite의 FTS5 토크나이저 제한에 의한 것이며, 정상 동작입니다.

## 5. 동영상 재생 최적화

### Faststart 캐시

MP4/MOV 파일의 동영상 재생을 가속화하기 위해 faststart 처리가 자동 적용됩니다.
faststart 처리된 동영상은 스트리밍 재생이 즉시 시작됩니다.

| 항목 | 값 |
|------|-----|
| 캐시 위치 | `cache/faststart/` |
| 용량 상한 | 4 GB (LRU로 자동 관리) |
| 1파일 상한 | 500 MB |
| 대상 | MP4, MOV (WebM은 불필요하므로 건너뜀) |

**체감 개선 기준**:

| 파일 크기 | faststart 미적용 | faststart 적용 |
|----------|----------------|---------------|
| 5-50 MB | 2-10초 대기 | 약 200ms에 재생 시작 |
| 50-200 MB | 10-60초 대기 | 약 500ms에 재생 시작 |
| 200-500 MB | 수분 대기 | 약 1초에 재생 시작 |

### FFmpeg 확인

faststart 처리에는 FFmpeg가 필요합니다. 설치되어 있지 않은 경우, 동영상은 전체 다운로드 후 재생됩니다.

```bash
ffmpeg -version
```

FFmpeg가 PATH에서 발견되지 않는 경우, [공식 사이트](https://ffmpeg.org/download.html)에서 설치해 주세요.

## 6. 메모리 사용량 관리

### SQLite mmap

대규모 데이터베이스 (10만 파일 이상)에서는 SQLite의 mmap (메모리 매핑 I/O)이 자동으로 1 GB로 설정됩니다.
이를 통해 읽기 쿼리가 OS의 페이지 캐시를 활용하여 가속화됩니다.

**RAM이 4 GB 이하인 환경**: mmap이 메모리를 압박할 수 있습니다.
이 경우 시스템의 여유 메모리를 모니터링하고, 스왑이 빈번하게 발생하면 다른 애플리케이션을 종료해 주세요.

### 브라우저 탭 관리

YU AI Manager는 SSE (Server-Sent Events)로 각 탭과 실시간 통신합니다.

- 1 IP당 최대 10 동시 SSE 연결
- 불필요한 탭을 닫으면 연결 리소스가 해제됩니다
- 많은 탭을 열면 브라우저의 메모리 사용량도 증가합니다

**권장**: 동시에 여는 탭은 3-4개 이내로 유지해 주세요.

## 7. 문제 해결 — 「느리다」고 느낄 때의 체크리스트

### 기본 확인

- [ ] **SSD를 사용하고 있는가**: `data/tags.db`가 HDD에 있는 경우 모든 조작이 느려집니다
- [ ] **FFmpeg가 설치되어 있는가**: 동영상 재생 가속화에 필수입니다
- [ ] **브라우저 탭 수**: 5개 이상 열려 있지 않은지 확인합니다

### 브라우징이 느린 경우

- [ ] **가상 스크롤을 활성화**: Settings > Appearance > Virtual Scroll
- [ ] **브라우저 캐시를 비우지 않기**: Service Worker의 캐시가 작동하고 있습니다
- [ ] **스캔 중인지 확인**: 스캔 중에도 정상적으로 사용할 수 있지만, 첫 썸네일 생성에 시간이 걸립니다

### 검색이 느린 경우

- [ ] **스캔을 완료시키기**: 스캔 완료 시 ANALYZE가 실행되어 검색이 최적화됩니다
- [ ] **검색 결과가 10만 건 초과**: 결과를 좁히는 필터 (태그, 날짜, 경로 등)를 추가해 주세요

### 동영상 재생이 느린 경우

- [ ] **FFmpeg 존재 확인**: `ffmpeg -version`으로 확인합니다
- [ ] **faststart 캐시 용량**: `cache/faststart/` 폴더가 4 GB를 초과하지 않았는지 확인합니다 (자동 관리이지만 확인 가능)
- [ ] **파일 크기**: 500 MB 초과 동영상은 faststart 캐시 대상 외입니다. Range 배신으로 재생되지만 처음에는 약간 느려집니다

### 서버 전체가 무거운 경우

- [ ] **동시 접속 수**: SSE 연결이 IP당 10을 초과하지 않았는지 확인합니다
- [ ] **업로드 중**: 100 MB 업로드 상한에 가까운 파일을 전송 중이 아닌지 확인합니다
- [ ] **Settings > Logs 탭**: 서버 로그에서 오류나 경고를 확인합니다

## 8. 성능 지표 기준값

정상적으로 최적화된 환경에서의 응답 시간 기준값입니다.

| 조작 | 28만 파일 규모 | 10만 파일 규모 |
|------|-------------|-------------|
| 그리드 표시 (최초) | 200-500ms | 100-300ms |
| 그리드 표시 (캐시 있음) | 50ms 이하 | 50ms 이하 |
| 태그 검색 | 100ms 이하 | 50ms 이하 |
| 경로 검색 (FTS5) | 50ms 이하 | 30ms 이하 |
| 썸네일 (캐시 히트) | 5ms 이하 | 5ms 이하 |
| 동영상 재생 시작 (faststart 완료) | 200ms | 200ms |

이 값을 크게 초과하는 경우, 위 체크리스트를 확인해 주세요.

## 고속 모드 (Rust 서버)

지원되는 환경에서는 시작이 자동으로 Rust 서버(`yu-server`)로 전환됩니다.

설정 -> "서버" -> "고속 모드"에서 **얻는 방법**을 고를 수 있습니다.

- **배포 바이너리를 내려받기**(기본값) -- 빌드하지 않습니다
- **이 기기에서 빌드** -- 내려받지 않습니다
- **내려받고, 실패하면 빌드**

빌드는 여유 디스크 8GB 이상이 필요하고 CPU와 메모리를 많이 사용합니다. **메모리가 적은 기기(라즈베리 파이 등)에서는 스왑을 다 써 시스템 전체가 다운될 수 있습니다.** 컴파일 중에도 모든 기능을 사용할 수 있습니다. Windows에서 빌드하려면 Visual Studio 빌드 도구(링커)가 별도로 필요합니다.

진행 상황은 같은 화면에 표시됩니다(경과 시간, cargo의 최신 줄, 성공·실패, 도중에 멈춘 경우 그 사실). 원본 로그는 `bin/fast-mode-build.log`에 있습니다.

web 번들이 오래되었거나 동봉 목록 밖의 확장이 있는 등 이 사본의 상태 때문에 고속 모드를 거부한 경우, 바이너리를 다시 가져와도 해결되지 않으므로 다운로드도 빌드도 하지 않습니다. 그 이유도 같은 화면에 나옵니다.
