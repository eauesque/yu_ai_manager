# LAN Cowork의 네트워크 동작（LAN에서 일어나는 일）

> 대상: v4.538.0 이상의 Rust standalone（`yu-server`）. Python 백엔드 병행（hybrid）구성의 경우
> 말미의 「Python 버전과의 차이」를 참조하십시오.

이 페이지는 **「LAN Cowork를 활성화하면 사용자의 머신이 네트워크 상에서 무엇을 시작하는지」**를
한 장에 정리한 것입니다. 설정을 변경하기 전에 읽어 보십시오.

---

## 요점

- **기본적으로는 아무것도 하지 않습니다.** Rust standalone은 뒤에 설명된 설정에서 명시적으로 활성화하지 않는 한,
  LAN 상에서 대기하거나 알림도 하지 않습니다.
- 활성화하면 **동일 LAN 상의 다른 노드에서 발견 가능한 상태**가 됩니다. 이는 설계대로의 동작입니다.
- **PIN의 유무는 discovery 알림을 중단하지 않습니다.** 자세한 내용은 「PIN과의 관계（오해하기 쉬운 점）」를 참조하십시오.

---

## 활성화하면 시작되는 것

| 동작 | 내용 |
|---|---|
| **UDP 대기** | `0.0.0.0:19850`을 bind합니다（모든 인터페이스） |
| **정기적인 알림** | 10초마다 서명된 HELLO를 `255.255.255.255:19850`으로 broadcast합니다. 내용에는 자신 노드의 ID·공개 키·API 포트·호스트명 등이 포함됩니다 |
| **다른 노드 등록** | 수신한 HELLO의 서명을 검증하고, 상대 노드를 자신의 피어 목록에 기록합니다（TOFU） |
| **inbound HTTP 수령** | 아래 표의 peer 용 엔드포인트가 응답을 반환하기 시작합니다 |
| **로컬 전달** | 수락된 피어 이벤트를 로그인 중인 화면이 구독하는 SSE（`/api/events/stream`）로 전달합니다 |
| **만료된 항목 정리** | 60초마다 만료된 페어링 요청과 평문 PIN을 메모리에서 정리합니다 |

### inbound에서 수령하는 엔드포인트

| 엔드포인트 | 인증 |
|---|---|
| `GET /ext/lan_cowork/api/peer/discover` | **세션 불필요**（피어 목록 조회） |
| `GET /ext/lan_cowork/api/peer/status` | **세션 불필요**（자신 노드의 설명자） |
| `POST /ext/lan_cowork/api/peer/register` | **세션 불필요**（피어의 자체 등록. 등록 대상은 서버 측에서 검증） |
| `POST /ext/lan_cowork/api/peer/pair/request` / `pair/verify` | **세션 불필요**（페어링 시작. 페어링되지 않은 상대는 세션을 가질 수 없음） |
| `POST /ext/lan_cowork/api/peer/token/renew` | 서명 + nonce（Bearer 불필요） |
| `POST /ext/lan_cowork/api/peer/event` / `heartbeat` | 서명 + Bearer 토큰 |

「세션 불필요」는 **인증이 없다**는 의미가 아니라 **로그인 세션을 요구하지 않는다**는 의미입니다.
페어링 완료되지 않은 상대는 세션을 가질 수 없으므로 이 5가지 경로만 예외적으로 개방되어 있습니다.
그 이외의 경로는 종전대로 로그인이 필요합니다.

## 활성화·비활성화 방법

`config.json`의 **`extensions` 섹션**에서 전환합니다.

```json
{
  "extensions": {
    "builtin-lan-cowork": {
      "enabled": true
    }
  }
}
```

- **키가 없으면 「비활성화」**입니다（Rust standalone）.
- 반영에는 **재시작**이 필요합니다.
- 일시적으로 전환하려면 시작 옵션에서도 지정할 수 있습니다. 우선순위는
  **커맨드라인 > `config.json` > 환경 변수 > 기본값**입니다.

| 방법 | 활성화 | 비활성화 |
|---|---|---|
| 커맨드라인 | `--native-daemon` | `--no-native-daemon` |
| 환경 변수 | `YU_LAN_COWORK_NATIVE_DAEMON=1` | 같음 `=0` |

> 환경 변수는 `1` / `true` / `yes`만을 「활성화」로 해석합니다. `on` 이나 `Y`는 **비활성화**로 취급됩니다.

### 활성화되어 있는지 확인하기

```bash
curl -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5000/ext/lan_cowork/api/peer/status
```

| 응답 | 의미 |
|---|---|
| `200` | 활성화. 피어 기능이 동작 중입니다 |
| `405` | **비활성화**（기능 자체가 내장되지 않은 상태） |
| `503` | 활성화이지만 준비되지 않음（노드 고유 키 미생성 또는 내부 초기화 실패） |

> **화면의 확장 기능 목록 표시는 믿을 수 없습니다.** 확장 기능 목록에서 LAN Cowork가 「활성화」로
> 표시될 수 있지만 이는 포함된 정보 기반의 표시이며 **위의 daemon이 실제로 동작하는지
> 여부와는 별개**입니다. 판단은 위 엔드포인트의 응답 또는 시작 로그의
> `native_daemon=...` 행으로 해야 합니다.

## PIN과의 관계（오해하기 쉬운 점）

**PIN을 설정하지 않았으면 LAN에서는 아무것도 만질 수 없다고 생각하는 것은 정확하지 않습니다.**

- **올바른 해석**: `--lan`（모든 인터페이스에서 대기）을 사용하려면 PIN이 필수이며, PIN이 없으면 시작이 중단됩니다.
  기본 대기는 `127.0.0.1`이므로 **일반적인 시작에서는 HTTP 면이 LAN에서 접근할 수 없습니다**.
- **주의 1**: `--host`에 LAN의 IP를 직접 지정한 경우 이 PIN의 필수 확인을 통과합니다.
  추가로 PIN 미설정 시에는 로그인 게이트 자체가 열리므로 **PIN 없이 LAN에 노출하는 것을 피해야 합니다**.
- **주의 2**: **UDP 알림은 PIN 설정 여부와 무관합니다.** 활성화되어 있으면 PIN 미설정 노드도
  10초마다 LAN에 자신의 존재를 broadcast합니다. PIN은 HTTP 면의 노출만 제한합니다.

즉, **PIN은 HTTP 면의 노출을 억제하지만 discovery 알림은 중단하지 않습니다.**

### loopback에서만 대기하는 경우（v4.539.0 이후）

대기 주소가 loopback 전용인 경우（기본값 `127.0.0.1`이며 데스크톱 버전에도 해당）,
**이 노드는 LAN에 알리지 않습니다**. 알리더라도 다른 노드가 연결할 수 없기 때문입니다.
시작 후 다음 경고가 한 번만 로그에 기록됩니다（INFO가 아닌 WARN이므로 기본 설정에서도 보입니다）.

```
LAN Cowork discovery inactive: server listens on loopback only; bind a LAN address or use --lan
```

LAN에서 사용하려면 LAN 주소에 bind하거나 `--lan`을 사용하세요（`--lan`에는 PIN이 필요합니다）.

> v4.539.0 이전에는 loopback 전용 대기 상태에서도 LAN IP를 알렸습니다. 상대 노드는 발견할 수 있지만
> 연결할 수 없었기 때문에 이 동작을 변경했습니다.

## 활성화하기 전에 알아야 할 것

- **비활성화해도 활성화되어 있던 동안 기록된 피어 정보는 자동으로 되돌려지지 않습니다.** 또한
  **활성화 후 처음 시작한 시점에** 오래된 피어 기록의 정리가 실행됩니다
  （마지막으로 도달 가능했던 때부터 7일 이상 경과한 기록 및 페어링되지 않은 채 1시간이 경과한 기록이 삭제됨）.
  전환하기 전에 `tags.db`의 백업을 취할 것을 권장합니다.
- 받은 피어 이벤트는 로그인 중인 화면이 구독하는 SSE로 전달됩니다. **내용은 상대 노드 유래의 입력**입니다
  （송신원 ID는 서버 측의 인증된 값으로 대체됨）.
- 로그에 남는 것은 **건수와 종별과 송신원 ID뿐**이며 이벤트의 내용은 기록되지 않습니다.
- 동작 상황을 확인하려면 로그 레벨에서 INFO를 활성화해야 합니다
  （예: `RUST_LOG=yu_server=info`）. 기본값 상태에서는 피어 이벤트 수신을 나타내는 행이 출력되지 않습니다.

## Python 버전과의 차이

| | Python 백엔드 병행（hybrid） | Rust standalone |
|---|---|---|
| 기본값 | **활성화**（`config.json`에 항목이 없으면 활성화） | **비활성화**（명시적인 활성화 필요） |
| 구현 | Python 확장 기능이 담당 | `yu-server`가 담당 |

**Rust standalone은 의도적으로 「기본적으로 비활성화」되어 있습니다.** 업데이트했을 뿐인데 네트워크 상의 동작이
변경되는 것을 피하기 위함입니다. hybrid 구성의 동작은 종전과 변함없습니다.

> 과거 문서에서는 활성화 설정을 `{"lan_cowork": {"enabled": true}}`（최상위）로 안내했지만
> **이 위치의 키는 어떤 구현에서도 읽어지지 않습니다.** 위의 `extensions` 섹션이 정확한 위치입니다.
